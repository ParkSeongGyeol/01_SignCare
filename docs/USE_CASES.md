# 유스케이스 목록

목록 버전: UC0.1 / 작성·갱신: 2026-10-18 (Asia/Seoul)
참조 명세: [v0.3](REQUIREMENTS_SPECIFICATION.md) / 관련 설계: [D0.1](design/DESIGN.md)
상세 명세: [UCS0.1](USE_CASE_SPECIFICATION.md) — 각 사례에 요청한 일곱 항목을 작성했다. 목록 ID·개요는 이 문서, 상세 조건·흐름·품질 연결은 명세서에서 관리한다.
상태: 기존 대화·요구를 목적별로 정리한 분석 초안. 사용자 상세 합의나 첫 배포 범위 확정을 뜻하지 않는다.

이번에는 기존 기능을 분류하고 추적 관계를 보완했다. 새 기능·수용 기준을 추가하지 않았으므로 명세 v0.3과 설계 D0.1을 유지한다. 목록 ID를 부여한 날짜와 해당 요구의 최초 도입일은 구분한다. 요구 도입 버전은 [변경 이력](REQUIREMENTS_CHANGELOG.md)을 따른다.

## 1. 유스케이스를 나누는 기준

사용자가 시스템을 통해 이루려는 목적과 그 완료 결과를 중심으로 나눈다. 예를 들어 '계획 화면 열기'보다 '기간별 계획을 검토하고 승인하기'가 목적을 잘 설명한다.
앱을 직접 열지 않는 흐름도 포함한다. 외부 자료가 도착해 시작하는 수집 흐름은 사용자 목적을 지원하는 외부 연동 유스케이스로 따로 표시한다.

- 사용자 목적 중심 18개와 외부 연동 2개를 식별했다. 기존 전체 여정 2개는 별도로 연결하며, 20개에 중복 합산하지 않는다.
- '사용자 방향'은 대화에서 목적이 확인됐다는 뜻이다. 아래 이름·분할·세부 흐름은 분석 제안이며 전부 승인됐다는 뜻이 아니다.
- '개발 제안'은 명세에 이미 제안으로 남아 있는 내용이다. 목록 작성으로 확정 요구로 승격하지 않는다.
- 중복 검사·저장·권한 검사·AI 호출은 각 흐름의 내부 동작이나 공통 규칙으로 다룬다. 별도 사용자 목적이라고 무조건 분리하지 않는다.
- 권한 거부·응답 없음·동기화 지연·생성 실패는 우선 해당 유스케이스의 대안·예외 흐름으로 다룬다.
- 아래 흐름의 시간 순서만으로 UML의 `include`나 `extend` 관계를 정하지 않는다. 상세 시나리오를 비교한 뒤 필요할 때 관계를 추가한다.

## 2. 시스템 경계와 액터

시스템 경계는 우리가 만드는 Android 앱과 그 앱이 책임지는 기록·분석·추천·계획 관리 기능이다. Flutter 화면, 내부 저장소, 분석 모듈은 내부 구성 요소이므로 액터로 나열하지 않는다.

| 액터 | 역할 | 현재 경계·미정 사항 |
|---|---|---|
| 사용자 | 관리 방향 선택, 짧은 응답, 기록·분석 확인, 계획 검토·승인·실행 | 주 사용자 1명. 별도 관리자·코치·의사 역할은 현재 요구에 없음 |
| 결제 자료 제공 시스템 | 지원되는 결제·정정·취소 자료를 앱에 제공 | 삼성페이·카드사 앱 알림이 초기 검증 후보. 금융 원장 전체 조회·과거 내역 복원은 보장하지 않음 |
| 건강·활동 자료 제공 시스템 | 허용한 걸음·운동 자료를 제공 | Samsung Health·Health Connect 경로가 검증 후보. 워치를 앱이 직접 읽는다고 가정하지 않음 |
| Android 권한·알림 시스템 | 권한 부여 상태, 알림 전달, 지원되는 버튼·답장·잠금 상태 동작 제공 | 보조 액터. 항상 표시·즉시 전달·인증 없는 응답을 보장하지 않음 |

외부 AI 서비스를 선택하면 분석·제안 흐름의 보조 액터로 추가할 수 있다. 공급자·외부 전송 범위는 미정이므로 현재 필수 액터로 확정하지 않는다. 시각 도래는 트리거로 적고 별도 사람 액터로 만들지 않는다. 구체적 연동 후보와 검증 범위는 [연동 검토](INTEGRATION_OPTIONS.md)를 따른다.

| UC-SETTINGS-001 | 알림·정보 노출과 데이터 처리 범위 확인하기 | 사용자: 설정 확인·조정 | 지원되는 알림·잠금화면 노출을 조정하고 외부 전송·보관·삭제 정책 확인 | REQ-INTERACT-001, NFR-LOCK-001, NFR-PRIVACY-001 | 노출 제어는 요구, 상세 기본값·정책은 개발 제안. 실제 데이터 삭제 실행 기능까지 확정한 것은 아님(Q-07/Q-13) |

수집은 초기 관찰과 계획 실행 양쪽에서 계속된다. 계획 승인 여부를 UC-EXPENSE-001·UC-ACTIVITY-001·UC-RECORD-001의 전제조건으로 두지 않는다.

## 4. 기존 시나리오와의 관계·중복 경계

| 기존 ID | 수준·유지 방법 | 연결되는 목적·연동 사례 |
|---|---|---|
| UC-ROUTINE-001 | '기존 루틴 파악과 첫 변경 제안' 전체 여정으로 유지. 별도 신규 기능으로 세지 않음 | 방향·여건·연결 확인 → 지속 수집·필요한 응답 → UC-ANALYSIS-001/002 → UC-CHANGE-001 → UC-PLAN-001 |
| UC-CAPTURE-001 | '사건 기반 자동 수집과 빠른 확인' 전체 여정으로 유지. 별도 신규 기능으로 세지 않음 | UC-EXPENSE-001 또는 UC-ACTIVITY-001 → 필요한 경우 UC-INTERACT-001/002 → 기록·분석에 사용 |
| UC-PLAN-001 | 기존 목적 단위의 검토·수정·승인 흐름을 그대로 목록에 포함 | 계획 생성·초안 수정·승인 성공/취소/저장 실패는 이 사례의 흐름. 승인 후의 변경은 UC-PLAN-002 |

위 화살표는 여정의 연결을 설명하며 UML `include`·`extend` 표기가 아니다. UC 이름의 숫자는 실행 순서나 중요도를 뜻하지 않는다.

겹쳐 보이는 사례의 경계:

- UC-INTERACT-002는 짧은 응답을 전달·저장하는 공통 상호작용이다. UC-ACTION-001은 실제 수행 결과를 남기는 업무 목적이며 빠른 응답 또는 앱에서 수행할 수 있다. 두 흐름이 만났다고 기록을 두 번 만들지 않는다.
- UC-RECORD-001은 실제 기록의 조회·누락 보완·정정, UC-ANALYSIS-002는 기록에 대한 해석의 정정이다.
- UC-BUDGET-001은 지출·예상 비용 확인, UC-REVIEW-001은 실행 결과까지 묶어 다음 조정을 검토하는 흐름이다.
- UC-GOAL-001의 방향 변경은 조건의 변경이다. 그 결과 기존 승인 계획을 변경하려면 UC-PLAN-002의 검토 경계를 지킨다. 자동 변경 권한은 별도 합의 전이다.

## 5. 상세 명세 형식과 작성 예시

사용자의 2026-10-18 요청에 따라 [유스케이스 명세서 UCS0.1](USE_CASE_SPECIFICATION.md)에 20개 사례와 전체 여정 2개를 다음 형식으로 작성했다.

> 개요 → 관련 액터 → 우선순위 → 선행 조건 → 후행 조건 → 이벤트 흐름 → 비기능 요구사항

대표 작성 예시는 [UC-INTERACT-002: 빠른 확인](USE_CASE_SPECIFICATION.md#uc-interact-002)이다. 기본 흐름과 잠금 제약·미응답·반복 응답·저장 실패를 함께 기술했다. 개별 명세의 우선순위는 검토 순서의 제안이고 품질 수치·미정 정책은 별도 합의 전이다.

## 6. 다음 검토 순서 — 제안

상세 초안을 작성했으므로 다음에는 아래 순서로 흐름과 미정 정책을 검토·구체화한다.

1. UC-EXPENSE-001 + UC-INTERACT-002: 무엇이 자동으로 들어오고 무엇만 물을지, 미분류·중복·응답 없음·저장 실패를 정의한다. 가장 큰 입력 부담을 먼저 확인한다.
2. UC-ACTIVITY-001: 지원 자료·권한·출처·지연·중복을 정의한다. 결제 사례와 공통 규칙·차이를 비교한다.
3. UC-ANALYSIS-001: 분석 대상 기간·실제 기록 범위·근거·정보 부족을 정의한다(Q-08).
4. UC-PLAN-001/002: 초안 승인·변경 적용의 단위와 실패 보장을 정의한다(Q-01/Q-06).

이 순서는 상세 명세 검토의 제안이며 첫 배포 포함 범위나 개발 일정의 확정이 아니다. 각 사례의 일곱 항목 안에서 트리거·기본 흐름·대안/예외·성공/중단 결과·연결 요구와 품질 검증을 함께 확인한다.

## 7. 현재 목록에서 확정하지 않은 것

PC 동기화, 체중·근육량 정밀 측정, 금융기관 직접 API·과거 내역 파일 가져오기, 사진·영수증 인식, 상세 식재료 재고·유통기한 관리, 장보기 전용 목록 관리, 계정·로그인, 데이터 삭제 실행, 변경의 자동 적용 위임은 후속·미정 사항이다. 기존 계획 문서에 후보로 등장해도 이번 20개와 같은 확정 수준으로 포함하지 않는다.
상시 강제 잠금화면 표시, 모든 사건의 즉시·완전 수집, 의료 진단, 특정 신체 변화 보장은 현재 요구로 두지 않는다.

유스케이스 목록은 상세 명세·UML 검토의 출발점이다. 코드의 UseCase 클래스 20개를 만들라는 구조 설계나 앱 기능 완료 목록으로 해석하지 않는다.
