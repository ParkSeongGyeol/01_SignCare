# 생활 데이터 연동과 알림 입력 검토

기준일: 2026-10-17 (Asia/Seoul)
상태: 공식 문서에 근거한 연동 후보와 검증 계획. 구현·기기 시험·금융 서비스 계약은 수행하지 않았다.

## 1. 제품 요구와 구현 후보 구분

사용자는 앱 사용 기간 내내 자동 수집을 우선하고, 식사·지출·운동 직후 앱을 찾아 열지 않아도 짧은 확인으로 기록하기를 원한다.
목표는 입력 부담 최소화다. 모든 거래·활동의 완전 자동 수집, 잠금화면 영구 표시, 동기화의 즉시성을 보장한 상태는 아니다.
3·7·15일 단위 패턴 분석과 매일의 상호작용·계획 조정이 요구된다. 누적·이동 기간의 선택과 자동 변경 권한은 아직 미정이다.
이 문서는 프로젝트 전체의 타당성 분석이 아니라 이 요구의 기술적 선택지 검토다.

## 2. 카드·식비 정보

### 2.1 금융기관 데이터 API — 후속 후보

금융결제원의 오픈뱅킹은 카드 청구 기본·상세 정보 등 조회 API를 제공하며 이용기관은 이용계약·승인을 받은 기관이다.
개인이 앱 하나를 만들었다는 이유로 모든 카드의 실시간 승인 내역을 바로 조회할 수 있다고 가정하지 않는다. 청구 정보와 실시간 승인 사건도 구별한다.
공급자별 제공 범위·이용 자격·인증·동의·비용을 확인한 뒤 선택해야 한다. 마이데이터·중계 공급자를 쓰는 경로도 별도 조사 대상이며 계약 가능성을 확인한 것은 아니다.
근거: [금융결제원 오픈뱅킹 공식 안내](https://openapi.kftc.or.kr/service/openBanking).

### 2.2 결제 알림에서 후보 만들기 — 초기 검증 후보

Android NotificationListenerService는 새 알림·제거·변경 사건을 받는 기능을 제공한다. 사용자가 시스템 설정에서 알림 접근을 허용한 뒤, 선택한 결제 알림 발신 앱을 대상으로 필요한 필드를 파싱하는 방식을 검토한다.
알림 접근은 금융기관 원장 조회가 아니며, 임의의 과거 카드 내역 전체를 복원하는 경로가 아니다.
근거: [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

제안 처리:

1. 사용자가 연결할 알림 출처를 선택하고 접근 범위를 확인한다.
2. 지원하는 결제 알림에서 가맹점·금액·시각 등의 후보를 추출한다.
3. 식사·장보기·기타 분류가 불확실한 경우 짧은 확인을 요청한다. 자동 분류·저장 허용 범위는 별도 합의한다.
4. 이미 처리한 사건, 알림 갱신, 취소·환불, 여러 앱에서 온 동일 거래 후보를 구분한다.
5. 동기화 단절·미지원 형식·가려진 값은 누락 가능성으로 표시하고 실제 지출 0원으로 처리하지 않는다.

알림 발송 설정·본문 형식에 따라 얻을 수 있는 항목이 다르다. Android 15는 OTP 감지 알림의 민감 내용을 비신뢰 알림 리스너에 가린다. 모든 결제 알림을 읽을 수 있다고 일반화하지 않는다.
근거: [Android 15의 알림 보호](https://developer.android.com/about/versions/15/behavior-changes-all).

카드 승인 후보를 읽어도 실제로 먹은 음식·섭취량·식사 여부는 알 수 없다. 결제 시각과 섭취 시각도 다를 수 있다.
혼합 구매나 공동 결제의 식비 몫은 필요 시 확인한다. 장보기 결제와 이후 끼니별 원가를 이중 집계하지 않는다.
문자 앱에 게시된 알림을 읽는 것과 SMS 저장소 전체를 읽는 권한은 다른 경로다. SMS 전체 읽기는 이번 초기안의 전제로 두지 않는다.

### 2.3 내역 파일 가져오기 — 보완 후보

카드사가 제공하는 이용내역 파일을 사용자가 내보낼 수 있다면 최초 과거 기록이나 누락 보완에 활용할 수 있다.
실제 카드사의 내보내기 지원과 형식·필드는 확인 전이다. 이 방법은 반복 자동 수집 자체를 대신하지 않는다.
중계 API·알림·파일·직접 입력 사이의 중복을 통합할 규칙을 설계해야 한다.

## 3. 삼성 헬스·갤럭시워치

우선 후보는 `Galaxy Watch → 휴대폰 Samsung Health → Health Connect → 우리 앱`이다.
삼성 공식 FAQ는 걸음·운동 등의 동기화와 워치의 간접 데이터 접근을 안내한다. 워치에서 휴대폰으로 넘어오는 시점은 자체 정책에 따르므로 운동 종료 즉시 도착을 보장하지 않는다.
근거: [Samsung Health / Health Connect FAQ](https://developer.samsung.com/health/health-connect-faq.html).

초기 검증 대상은 걸음 수, 운동 종류·시작/종료 시각·시간이다. 실제 제공 필드와 집계 방식은 연결 기기·앱 버전에서 확인한다.
백그라운드 읽기는 지원 여부와 추가 권한을 확인해야 한다. Android 공식 예제도 해당 기능의 가용성을 확인하고 사용자 권한에 맞춰 동작한다.
근거: [Health Connect 데이터 읽기](https://developer.android.com/health-and-fitness/health-connect/read-data).

출처·원본 ID·관측 시각·가져온 시각·수정/삭제를 추적하고 반복 동기화에 멱등성을 둔다.
휴대폰과 워치 등 여러 출처의 걸음 수를 단순 합산하지 않는다. Health Connect 집계·출처 우선순위와 중복 방지 방법을 설계에서 검토한다.
데이터가 아직 도착하지 않았거나 권한이 없으면 '운동하지 않음'으로 판정하지 않는다.
사용자가 이미 제공한 기록을 반복해서 수동 입력하게 하지 않으며, 체감 부담처럼 자동으로 알 수 없는 내용만 선택적으로 묻는다.

Samsung Health Data SDK 직접 연동은 대안으로 남긴다. 필요한 기능의 지원·접근 조건과 패키지 배포 조건은 별도 확인하며 Health Connect보다 적합하다고 확정하지 않았다.
근거: [Samsung Health Data SDK](https://developer.samsung.com/health/data/overview.html).

## 4. 앱을 열지 않는 상호작용과 잠금화면

### 4.1 우선 후보: 알림의 고정 버튼·짧은 답장

Android 알림은 빠른 동작 버튼과 RemoteInput 답장을 지원한다. 짧은 확인은 앱의 전체 화면을 열지 않고 처리할 수 있다. 잠금 상태·보안 설정에 따라 인증이 필요할 수 있다.
근거: [알림 생성·동작·직접 답장](https://developer.android.com/develop/ui/compose/notifications/create-notification), [동작의 인증 요구](https://developer.android.com/reference/android/app/Notification.Action.Builder#setAuthenticationRequired(boolean)).

예시 UI 후보 — 실제 사용자 정보가 아닌 문구 예시:

| 상황 | 기본 질문·안내 | 버튼 후보 |
|---|---|---|
| 결제 후보의 분류 불명 | 이 지출을 어떻게 분류할까요? | 식사 / 장보기 / 식비 아님 |
| 식사 기록 보완 | 식사 기록에 무엇을 더할까요? | 음식 추가 / 이전과 같음 / 나중에 |
| 운동 기록 도착 | 운동 기록을 가져왔어요 | 보기 / 체감 추가 / 나중에 |
| 실행 가능한 시간 | 계획한 행동을 지금 할 수 있나요? | 시작 / 미루기 / 오늘 어려움 |

운동처럼 이미 정확히 가져온 데이터는 확인 버튼을 누르지 않아도 수집 상태로 유지하는 방향이다. 확인되지 않은 체감이나 섭취 사실을 대신 만들어내지 않는다.
복잡한 분류·음식 선택은 알림에서 이어지는 짧은 입력 화면으로 제공할 수 있다. 화면 구조·문구·버튼은 상세 설계에서 결정한다.

### 4.2 잠금화면에 항상 띄우고 싶은 요구

잠금화면에 표시할 알림을 제공하는 것은 가능하지만 표시 여부·본문 노출·채널은 사용자가 최종 제어한다. 상주 알림도 Android 14부터 잠금 해제 상태 등에서 해제될 수 있다.
따라서 요구는 '사용자가 허용한 잠금화면 알림에서 빠른 기록 제공'으로 다듬고, '항상 켜짐·삭제 불가·전체 잠금화면 대체'를 보장하지 않는다.
근거: [잠금화면 알림 제어](https://developer.android.com/develop/ui/compose/notifications/create-notification), [Android 14 상주 알림 변경](https://developer.android.com/about/versions/14/behavior-changes-all).

전체 화면 호출은 전화·알람 등 긴급한 용도로 제약되므로 일상 기록의 기본 구현으로 채택하지 않는다.
근거: [Android 14 전체 화면 알림 제약](https://developer.android.com/about/versions/14/behavior-changes-14).

금액·가맹점·건강 목표 등의 상세 내용은 기본 잠금화면 문구에서 감추고, 노출 범위를 선택 가능하게 하는 안을 제안한다.
상주 알림을 선택하지 않아도 사건별 알림·홈 화면 진입점·앱 내 미처리 항목으로 기능을 이어가는 안을 검토한다. 모든 기기의 잠금화면 위젯을 기본 전제로 두지 않는다.

### 4.3 사건 발생과 데이터 도착을 구분

Android 13 이상에서는 일반 알림 게시 권한이 필요하다. 알림 접근, 건강 데이터 읽기, 알림 게시 권한은 각각 별개다.
알림 허용·방해 금지·배터리 정책·강제 종료·권한 회수 등의 영향을 시험해야 한다.
위 알림 생성 문서가 일반 게시 권한을 설명한다.

WorkManager 주기 작업은 최소 반복 간격과 시스템 스케줄링 제약이 있다. 수집 주기를 줄였다는 이유만으로 운동 종료 시점의 실시간 감지를 약속하지 않는다.
도착한 결제·운동 사건으로 확인 요청을 만들고, 도착하지 않은 항목은 동의한 시간대에 보완 질문하는 방식을 제안한다.
근거: [WorkManager 작업 정의](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

같은 사건에 대한 반복 알림을 억제하고, 묶음 확인·미루기·조용한 시간·빈도 설정을 제공하는 방향이다. 정확한 임계값은 미정이다.

## 5. 지속 수집·분석·계획 조정

- 초기 관찰 이후에도 같은 수집 경로를 계속 사용한다. 3·7·15일을 수집 종료일로 취급하지 않는다.
- 3일의 초기 경향, 7일의 반복 경향, 15일의 변화 검토는 제품 분석 단계 제안이다. 각 기간이면 통계적으로 패턴이 확정된다는 주장은 하지 않는다.
- 누적·이동 분석 창, 달력일과 기록일의 기준, 데이터 충족 조건, 지연 도착 시 재분석 방법은 요구 상세화 대상이다.
- 매일의 새 정보·사용자 응답으로 계획 변경 초안을 제안할 수 있다. 실제 기록과 기존 승인 계획을 무조건 덮어쓰지는 않는다.
- 알림에서 간단히 변경을 승인할 수 있는 범위와 사전에 위임할 수 있는 작은 조정의 범위를 구분해 결정한다. 자동 적용 권한은 아직 합의하지 않았다.

## 6. Flutter 적용과 검증 순서 — 제안

Flutter/Dart를 유지한다. 화면 외의 Android 연동은 검증된 플러그인 또는 플랫폼 채널을 통해 네이티브 기능과 연결할 수 있다.
특정 패키지의 백그라운드·잠금 상태 지원은 확인하지 않았다.
근거: [Flutter 플랫폼 채널](https://docs.flutter.dev/platform-integration/platform-channels).

우선 작은 연동 시험으로 다음을 확인한다.

1. 대상 기기의 Health Connect 가용성, 삼성 헬스 연결, 운동·걸음 수 가져오기와 동기화 지연
2. 잠금·해제 상태에서 알림 버튼·직접 답장, 권한 거부·재부팅·오프라인 시 처리
3. 사용자가 선택한 결제 알림 출처의 가상 형식으로 추출·중복·취소 처리. 실제 금융 원문을 공개 저장소에 넣지 않음
4. 가져온 정보를 미리 채운 고정 선택 UI로 기록을 완료하는 동작 수·소요시간
5. 하루 알림 수·무응답·수정 빈도를 보고 입력 부담과 누락을 평가

사용자 제공 시험 환경은 퀀텀3, Android 16·One UI 8.0, 갤럭시워치 8, 삼성페이 또는 카드사 앱 결제 알림이다. 이는 사용자 제공 정보이며 실기 확인은 아직 하지 않았다. 카드사별 형식과 실제 알림 접근 가능 범위는 미확인이다.
민감한 계정 정보나 거래 원문은 요청하지 않았다.
현재는 문서 조사만 수행했으며 자동 연동이나 알림이 실제로 작동한다고 검증한 상태는 아니다.
