# 프로젝트 맥락 및 대화 요약

기준일: 2026-10-18 (Asia/Seoul)

## 1. 앱을 만드는 이유

개인이 계속 사용하고 수정할 수 있는 건강관리 튜터 에이전트를 만든다.
건강관리와 식비 계획을 일상에서 실행할 수 있도록 돕는 것이 목적이다.
최신 방향은 며칠간 기존 루틴을 먼저 파악하고 생활패턴과 실행 여건에 근거하여 긍정적인 변경을 제안하는 것이다.
카드·건강 데이터 연동을 활용해 사용 기간 내내 자동 수집하고, 앱이 먼저 알림과 고정 선택 UI로 짧은 확인을 유도하여 입력 부담을 최소화한다.
AI가 요리할 메뉴, 조리 방법, 요리하기 어려울 때 먹을 수 있는 대안 등 실제로 실행할 수 있는 지침을 주기를 원한다.

사용자가 기대하는 결과:

- 사용자가 선택한 체중 증량·유지·감량 방향의 일상 관리
- 운동 지침에 따른 생활 변화 지원. 체중·근육량 변화의 정밀 측정은 후속 검토
- 효율적인 식비 활용과 사용자가 설정한 예산에 맞춘 식비 절감

이는 제품의 목표이며 앱이 결과를 보장한다는 뜻은 아니다. 구체적인 건강 목표와 수치, 평가 방법은 아직 정하지 않았다.

| 일정 계산의 가용 시간 | 주 20시간 |
| 맥락 보존 | 다른 세션에서도 읽을 수 있도록 대화와 결정 내용을 프로젝트 문서로 유지 |

VS Code는 사용자가 Flutter와 함께 검토한 개발 도구다. 사용 가능하지만 설치·설정 완료 또는 최종 편집기 선택을 확인한 상태는 아니다.

## 3. 지금까지의 대화 흐름

1. 사용자는 건강관리와 식비 절감을 돕는 개인용 AI 튜터 앱을 구상하고, 설계부터 제작까지 단계적으로 도움을 요청했다.
2. 초기 제안은 오늘의 계획, 식사 선택, 빠른 기록, 주간 점검을 중심으로 작은 버전을 만들자는 것이었다. 기술 후보로 React Native + Expo를 제안했다.
3. 사용자는 Android를 쓴다고 밝혔고, 조리 환경 전체를 입력하기보다 기본 목록에서 없는 도구를 빼는 방식을 요구했다. 식비 현황과 목표를 제시했다.
4. 사용자는 오늘의 남은 식비를 기준으로 움직이는 방식보다 월·주 계획을 제안·승인한 뒤 수정하는 방식을 선호한다고 정정했다. Flutter와 VS Code의 개발 난이도를 질문했다.
5. 이에 월간 방향, 주간 계획, 검토·승인, 실행 중 조정, 주간 점검을 제안했다. Flutter도 적합하며 초기 도구 설정과 Dart 학습이 필요하다고 설명했다.
6. 사용자가 Flutter로 진행하기로 결정했다. 대화 맥락의 문서화와 소프트웨어 공학 관점의 개발 절차 설명을 요청했다.
7. 사용자가 기존 GitHub 저장소의 파일을 현재 프로젝트로 교체하고 이후 개발 내용을 관리하도록 요청했다. 과거 커밋 이력은 유지하는 방식으로 진행한다.
8. 사용자가 GitHub 저장소 이름을 `01_SignCare`로 변경했다. 개발 저장소는 `ParkSeongGyeol/01_SignCare`이며, 이 변경만으로 앱의 공식 명칭이 확정된 것으로 해석하지 않는다.

## 4. 개발 방향으로 제안되었지만 아직 세부 확정되지 않은 내용

### 관찰·분석과 기간별 계획

- 기존 루틴을 먼저 관찰·분석하고 그 근거에 맞춰 변경을 제안하는 방향은 최신 사용자 요구다.
- 초기 지침 선택 시점, 요약·분석 결과 확인·정정 방식, 정보 부족 처리, 한 번에 제안할 변경 수는 개발 제안 또는 미정 사항이다.
- 3·7·15일 단위 분석과 계속되는 수집, 사건 직후 고정 UI·알림 상호작용은 최신 사용자 요구다. 누적·이동 창·데이터 충족·알림 빈도와 자동 변경 권한은 미정이다.
- 최초 관찰과 이후 실행은 같은 수집 경로를 사용한다. 모든 데이터가 즉시·완전하게 수집되거나 잠금화면이 영구 표시된다고 해석하지 않는다.

- 월간: 식비 한도, 건강·운동 방향, 외식 등에 쓸 예산의 큰 틀 설정
- 주간: 구체적인 식사와 운동, 장보기 목록, 예상 지출 제안 및 승인
- 일간: 승인된 계획의 실행 안내와 기록
- 변경: 일정, 재고, 선호 변화에 따른 수정 제안과 영향 확인
- 회고: 실제 지출과 실천 결과를 다음 계획에 반영

월간 방향과 주간 상세 계획을 나누는 것은 개발 제안이다. 정확한 계획 기간, 승인 범위, 간단한 변경을 처리하는 방식은 추후 설계한다.

### 추천과 기록

- 요리와 외식 대안을 함께 제공하고 조리 시간, 예산, 보유 재료 등을 고려한다.
- 장보기 총지출과 한 끼의 추정 원가를 구분한다. 두 값을 합산하여 식비를 중복 집계하지 않는다.
- 남은 식재료와 재사용 가능성을 고려한다.
- 예상 가격과 실제 결제액을 구분한다.
- 식사, 지출, 운동 기록의 입력 부담을 낮춘다.
- 자동으로 가져온 금액·활동은 재입력을 최소화하고, 섭취 음식·분류·체감 등 부족한 내용만 짧게 확인하는 안을 검토한다. 카드 결제만으로 실제 섭취 사실을 확정하지 않는다.
- 생활 기록만으로 체중·근육량의 변화를 추론하지 않는다. 초기에는 실행·지출·부담 등 생활 변화의 지표를 검토하고 정밀 신체 측정은 후속으로 둔다.

### 조리도구 기본값 초안

- 기본 가정: 냉장고·냉동실, 가열대, 전자레인지, 전기밥솥, 프라이팬, 냄비, 칼, 도마, 기본 식기
- 선택 확인: 에어프라이어, 오븐, 믹서 등
- 이 목록은 확인된 실제 보유 현황이 아니다. 수정 가능하게 제시한다.
- 쌀, 기름, 양념 등의 식재료·소모품은 도구와 별도로 확인한다.

### 기술 방향

- Flutter/Dart + Android 우선은 확정이다.
- PC는 웹 또는 Windows 설치형 앱을 후보로 검토한다. 아직 선택하지 않았다.
- 계정, 서버, AI 공급자, 저장소, 상태 관리 라이브러리, 동기화 방식은 미정이다.
- Flutter만 선택했다고 기기 간 데이터 동기화가 자동으로 구현되는 것은 아니다.
- 카드·건강 자동 수집과 잠금화면의 공식 지원 범위는 [연동·알림 검토](INTEGRATION_OPTIONS.md)에 정리했다. Health Connect, 선택한 결제 알림 추출, 알림 버튼·직접 답장이 초기 검증 후보이며 아직 채택·구현·시험하지 않았다.

## 5. 요구분석에서 해결할 질문

필요한 시점에 짧게 확인하고, 한 번에 긴 설문을 요구하지 않는다.

- 식비에 카페, 간식, 술, 배달료, 회사에서 제공받는 식사 등을 어떻게 포함할 것인가?
- 사용자가 설정한 월 예산의 정확한 경계와 초과 예상 시 안내·승인 규칙은 무엇인가?
- 월간 계획과 주간 계획은 각각 어느 수준으로 승인하는가?
- 이미 구매한 재료, 완료한 식사·운동, 승인된 계획 이력을 변경 시 어떻게 보존하는가?
- 조리 가능 시간, 반복 메뉴 허용 정도, 외식 일정, 재료 관리의 입력 범위는 어느 정도인가?
- 알레르기, 피해야 할 음식, 부상 등 추천에 필요한 제약은 무엇인가?
- 운동 경험, 운동 장소·도구·시간 및 목표를 어떻게 설정하는가?
- 증량·유지·감량 외에 어떤 일상·운동·식비 지침을 선택하며 상충 시 어떻게 조정하는가?
- 3·7·15일 분석 창과 최소 정보 충족 기준, 자동 수집 후 필수 확인 항목은 무엇인가?
- 연결 출처의 실제 지원·권한·누락·중복·취소를 어떻게 처리하고 잠금화면에서 무엇을 보여주는가?
- 오프라인에서 가능한 기능과 향후 동기화 범위는 무엇인가?
- 개인 건강·생활 데이터의 보관, 삭제, 외부 AI 전송 범위는 무엇인가?
- AI 사용료와 서버 운영비는 어느 정도까지 허용하는가? 식비와는 별도로 관리한다.

## 6. 이어서 작업할 때 지킬 해석

- 최신 요구인 기존 루틴 관찰·분석을 기간별 계획·승인보다 먼저 둔다. 일별 예산 중심의 초기 제안으로 돌아가지 않는다.
- 기존 React Native + Expo 제안은 채택되지 않았다. Flutter가 최종 결정이다.
- 현재 문서의 초기 모델과 아키텍처 후보는 확정된 구현 명세가 아니다.
- 사용자의 추가 발언이 있으면 관련 결정과 미정 사항을 갱신한다.
- 현재 계획은 [planning/PLAN.md](planning/PLAN.md)를 따른다. 4 KSLOC, 전체 Nominal 등급, 시간당 3만 원은 확정된 실제 규모·역량·단가가 아니라 계산을 위한 가정이다.
- [AI 보조 개발 연구](planning/AI_PRODUCTIVITY_RESEARCH.md)를 함께 확인한다. 기존 105.85주는 실무 일정으로 채택하지 않는다. 논문 수치로 일괄 할인한 새 일정도 아직 없다.
- 현재 요구분석 산출물은 [요구분석명세서 v0.3/R1](REQUIREMENTS_SPECIFICATION.md) 작성 완료·검토본이다. 지속 수집·사건 기반 알림·분석 단위와 매일 조정은 의도 확인 상태이며 구체적 지원 경로·수용 기준·분석 창·승인 권한은 초안 또는 미정이다. 문서의 완성과 정책·기준선 확정을 구분한다.
- 현재 작업 단계는 [기능·상호작용 설계 D0.1](design/DESIGN.md)이다. 화면·동작·자료 책임을 먼저 구체화하고 상세 아키텍처·클래스·패턴으로 이어간다. 새 요구나 동작 변경은 [명세 변경 이력](REQUIREMENTS_CHANGELOG.md)에 도입·변경 버전과 날짜를 남긴다.
- 최근 분석 보완은 [유스케이스 목록 UC0.1](USE_CASES.md)과 [상세 명세 UCS0.1](USE_CASE_SPECIFICATION.md)이다. 다음에는 수집·빠른 확인·분석·승인 사례의 우선순위·흐름·미정 정책을 검토하고 구체화하는 방안을 제안한다. 상세 설계 확정이나 구현 시작을 뜻하지 않는다.
