## 1. 이번 계획의 목적과 상태

사용자는 소프트웨어 공학 책의 기법을 프로젝트에 실제 적용하여 연습하고 싶다고 밝혔다.
이번에는 **개발 요소 도출 → COCOMO II 공수·비용 산정 → 작업 분해 → 의존관계 → CPM → 자원 제약 일정 → 간트 차트**를 수행한다.
사용자 요청에 따라 타당성 분석과 별도 위험분석은 작성하지 않는다.

확정된 입력은 Flutter/Dart, Android 우선과 **주 20시간**이다. 개발자는 사용자 본인 1인으로 가정한다.
제품 범위, 코드 규모, 계수 등급, 작업별 배분율, 단가는 추정을 위한 제안이다. 아직 실제 개발 기간을 약속하거나 설계를 확정한 것이 아니다.
이 문서의 비용은 제품의 식비 예산과 다른 **소프트웨어 개발 비용**이다. 개인 건강·지출 정보는 포함하지 않는다.

## 3. COCOMO II 모델 선택

**COCOMO II.2000의 Early Design 모델**을 사용한다. 아직 상세 구조와 패키지가 정해지지 않았으므로, Post-Architecture의 17개 공수 승수 대신 Early Design의 7개 승수를 사용한다.
COCOMO 81의 Organic/Semi-detached/Embedded 계수를 섞지 않는다.

산식:

```text
E      = B + 0.01 × ΣSF
PM_NS  = A × Size^E × ΠEM(단, SCED 제외)
PM     = PM_NS × EM_SCED
F      = D + 0.2 × (E − B)
TDEV   = C × PM_NS^F × (SCED% / 100)
시간   = PM × 152
인건비 = 시간 × 시간당 단가
```

- Size: KSLOC, 신규 납품 논리 소스 문장 천 개 단위
- PM: 인월. 공수 단위이며 달력상의 개월 수와 구별
- TDEV: 모델의 명목 달력 개발 기간. 개인의 주 20시간 일정을 뜻하지 않음
- 기본 상수: A=2.94, B=0.91, C=3.67, D=0.28
- SCED 공수 승수와 SCED% 일정 비율은 서로 다른 값이며 이번에는 각각 1.0, 100% 사용
- 1PM=152시간을 사용하며, 작업 시간에는 필요한 분석·설계·검증도 포함

근거: USC CSE 저작 [COCOMO II Model Definition Manual v2.1](https://www.rose-hulman.edu/class/cs/csse372/201310/Homework/CII_modelman2000.pdf)의 §2.1, §3, §4, §8.3.1(Tables 62–63), §8.4. 저자 기관의 원문을 대학 서버에서 제공하는 사본이다.
모델 구분 개요는 [Boehm CSSE](https://boehmcsse.org/tools/cocomo-ii/)도 참고한다.

## 5. 규모 요인과 공수 승수

개발자의 능력·경험과 프로세스를 평가할 근거가 없으므로 **모두 Nominal로 놓은 기준 계산**을 한다. 실제 사용자 역량을 표준 수준이라고 판정한 것이 아니다.

| SF | 의미 | 등급 | 값 |
|---|---|---|---:|
| PREC | 유사 프로젝트 경험 | Nominal | 3.72 |
| FLEX | 개발 유연성 | Nominal | 3.04 |
| RESL | 아키텍처·위험 해결 정도 | Nominal | 4.24 |
| TEAM | 팀 응집성 | Nominal | 3.29 |
| PMAT | 프로세스 성숙도 | Nominal | 4.68 |
| 합계 | | | 18.97 |

따라서 `E = 0.91 + 0.01 × 18.97 = 1.0997`.
별도 위험분석 문서는 생략하지만 RESL은 모델의 필수 규모 요인이므로 기준값을 유지한다.

| EM | 의미 | 등급 | 승수 |
|---|---|---|---:|
| PERS | 인력 역량 | Nominal | 1.00 |
| RCPX | 신뢰성·복잡성 | Nominal | 1.00 |
| PDIF | 플랫폼 난이도 | Nominal | 1.00 |
| PREX | 개발 경험 | Nominal | 1.00 |
| FCIL | 개발 시설·도구 | Nominal | 1.00 |
| RUSE | 재사용성 요구 | Nominal | 1.00 |
| SCED | 일정 압축 | Nominal | 1.00 |

`ΠEM = 1.00`. 패키지를 사용한다는 이유로 RUSE를 낮추거나, 생성형 AI를 사용한다는 이유로 임의 생산성 할인율을 곱하지 않는다.
RUSE는 다른 곳에서도 재사용되게 개발해야 하는 요구의 정도이며 외부 패키지 재사용량 자체가 아니다.

## 6. 계산 결과와 비용 해석

```text
PM     = 2.94 × 4^1.0997 × 1.00 = 13.5031 인월
시간   = 13.5031 × 152 = 2,052.47시간
F      = 0.28 + 0.2 × (1.0997 − 0.91) = 0.31794
TDEV   = 3.67 × 13.5031^0.31794 = 8.3961개월
```

모델 본체의 예시 인건비는 시간당 3만 원 가정 시 약 **6,157만 원**이다. 단가는 사용자 확정이 아닌 계산 예시다.
본인의 시간을 금액으로 환산한 값이며 실제로 지급해야 하는 현금이 아니다. 단가를 정하지 않으면 `2,052.47 × 시급`으로 해석한다.

TDEV 8.40개월은 모델이 암묵적으로 가정한 팀 운영 기준의 일정이다. 평균 투입은 `PM/TDEV ≈ 1.61명(모델상 전일제 상당)`이다.
개인 개발자가 주 20시간씩 개발하여 8.40개월에 끝난다는 결론으로 바꾸면 안 된다.
주 20시간의 단순 공수 환산은 본체만 `2,052.47/20 = 102.62주`다.

현재 계획은 COCOMO의 Waterfall 범위인 요구 기준선 이후부터 인수 검증까지를 본체로 매핑한다.
기준선 전 계획·요구 정리·환경 구성 48h와 인수 후 개인용 설치·운영 안내 16h는 외부 작업으로 별도 가정했다.
이 64h는 COCOMO 산출값이 아니다. 이미 수행한 과거 작업의 실측값도 아니며 앞으로의 작업 예산이다.

모델 공수를 정수 시간으로 올림하여 배분한 전체 일정은 **2,053 + 64 = 2,117h**, 주 20시간이면 **105.85주**다.
시간당 3만 원 예시의 전체 노동비용 환산액은 **6,351만 원**이다.
자동 계산의 비반올림 본체 비용과 일정용 정수 공수의 비용을 구분한다.

## 7. 작업 분해와 공수 배분

작업은 [model_inputs.json](model_inputs.json)의 `tasks`에 ID·선행 작업·완료 결과를 저장했다.
상세 작업별 시간과 ES/EF/LS/LF/TF는 [자동 계산표](CALCULATIONS.md)에 있다.

본체 2,053h를 다음 **제안 배분율**로 나눈다. 배분율은 COCOMO 공식이 정해준 값이나 독립적인 상향식 추정값이 아니다.
정수 시간 배분은 소수점 이하가 큰 항목부터 남은 시간을 배정하여 합계를 유지한다.

| P | 계획 산출물 정리 | 별도 8h | 없음 |
| R | 요구분석·기준선 | 별도 24h | P |
| E | Flutter 개발 환경 | 별도 16h | P |
| A | 화면·상호작용 설계 | 5% | R |
| B | 아키텍처·데이터 계약 | 5% | R, E |
| C | 클래스·패턴·테스트 설계 | 4% | A, B |
| D | 앱 골격·로컬 저장 | 7% | C |
| F | 프로필·환경·예산 | 5% | D |
| G | 기간 계획·승인·변경 | 18% | F |
| H | 식사·레시피·장보기 | 10% | G |
| I | 운동·오늘·실행 기록 | 7% | G |
| J | 지출·주간 점검 | 8% | G |
| K | 최소 서버·AI 연동 | 12% | C |
| L | 통합·회귀 테스트 | 10% | H, I, J, K |

현재 고정시간 작업에는 장기적인 Flutter 학습 시간을 별도로 가산하지 않았으며 필요하면 다시 추정한다.

## 8. 네트워크 차트와 CPM

활동을 노드로 표시하는 AON 네트워크를 사용한다. 모든 의존관계는 완료 후 시작(Finish-to-Start)이며 지연시간은 0이다.

```text
작업 기간 d = 배분 공수 / 주 20h
ES = 선행 작업 EF의 최댓값       EF = ES + d
LF = 후속 작업 LS의 최솟값       LS = LF − d
TF = LS − ES = LF − EF
```

시작 시점은 0이다. 표의 2.40은 특정 날짜가 아니라 프로젝트 시작 후 2.40주 경과 시점이다.
CPM은 여러 독립 작업을 수행할 자원이 충분하다고 가정하여 계산한다. 각 작업은 담당자 1명이 주 20시간 처리하는 기간을 사용한다.
즉, 동시 수행 시 여러 담당자가 필요하다. TDEV의 팀 인원·작업 배분을 그대로 재현한 네트워크는 아니다.

![AON 네트워크](network.png)

주공정은 두 개이며 A와 B는 병렬 분기다.

- P → R → A → C → D → F → G → H → L → M → N → Z
- P → R → B → C → D → F → G → H → L → M → N → Z

자원 무제약 완료 시점은 **72.20주**다. A와 B가 동시에 TF=0이라고 해서 A 다음에 B를 수행하는 하나의 논리적 주공정으로 표기하지 않는다.

## 9. 1인 자원 제약과 간트 차트

현재 개발자는 1명이므로 CPM의 병렬 작업을 그대로 실행할 수 없다.
선행관계를 만족하는 작업 순서 P, R, E, A, B, C, D, F, G, H, I, J, K, L, M, N, Z로 배치했다.
이 순서는 실행 가능한 하나의 제안이며, 실제 AI 연결을 일찍 검증하려면 K의 순서를 조정할 수 있다.
업무를 나눠 동시에 수행하는 대신 이 계획에서는 한 번에 한 작업만 배정한다.

![1인 자원 제약 간트 차트](gantt.png)

총 2,117h / 주 20h = **105.85주**, 즉 106번째 주 중 종료한다.
모든 업무의 담당자는 같은 개발자이며 어느 시점에도 주 20시간 용량을 초과하지 않는다.
대기시간·휴가·외부 승인 지연을 추가하지 않은 작업 용량 기준이다. 실제 착수일과 휴무일을 정한 달력 일정은 아직 아니다.
자원 무제약 TF는 1인 일정에서 그대로 사용할 수 있는 여유시간이 아니다. 1인 순차 배치에는 별도의 유휴 여유를 넣지 않았다.

## 10. 결과를 읽는 법과 다음 추정

이번 결과는 표준 계수로 계산한 **교과서 연습용 기준선**이다. 개인용 Flutter와 생성형 AI 보조 개발의 실측 생산성에 맞춰 보정한 모델이 아니다.
그래서 실제 완료일이 약 2년 뒤라고 확정하지 않는다. 그렇다고 원하는 일정에 맞추려고 계수나 코드 규모를 임의로 줄이지도 않는다.

다음에는 다음 순서로 근거를 개선한다.

1. 기능 범위와 요구 기준선을 정하고 SLOC 가정을 다시 검토한다.
2. 개발 환경과 작은 승인·저장 흐름을 구현하며 실제 공수·규모를 기록한다.
3. WBS 항목별 상향식 시간을 별도로 추정하고 COCOMO 결과와 비교한다.
4. 차이가 큰 이유를 분석한다. 규모, 범위, 등급, 모델 적합성, AI 보조 효과를 구분한다.
5. 입력과 계획 버전을 갱신한다. 소규모 실측만으로 검증된 AI 생산성 배수나 보편적 보정 계수를 주장하지 않는다.
