# 요구분석명세서

기능 버전: 0.3 / 문서 개정: R1 / 작성: 2026-10-17 / 갱신: 2026-10-18 (Asia/Seoul)
상태: 요구분석명세서 작성 완료·검토본. 사용자 결정·개발 제안·미정 사항을 구분하며 요구 기준선과 첫 배포 범위는 아직 확정하지 않았다.

변경 날짜·이유·요구별 도입 버전은 [명세 변경 이력](REQUIREMENTS_CHANGELOG.md)에 기록한다. 현재 설계는 [D0.1](design/DESIGN.md)이다. 이번 변경 이력 정리·설계 문서 작성은 기능 추가가 아니므로 명세 v0.3을 유지한다.
2026-10-18 분석 보완: [유스케이스 목록 UC0.1](USE_CASES.md)에 기존 요구의 액터·목적·결과·연결 ID를 정리했다. 기존 UC-ROUTINE-001·UC-CAPTURE-001은 전체 여정, UC-PLAN-001은 목적 단위로 유지한다. 이 정리는 새 기능·수용 기준 변경이 아니므로 v0.3을 유지한다.
같은 날 [유스케이스 명세서 UCS0.1](USE_CASE_SPECIFICATION.md)에 개요·관련 액터·우선순위·선행 조건·후행 조건·이벤트 흐름·비기능 요구사항을 작성했다. 우선순위·세부 흐름은 개발 초안, 미정 정책·품질 수치는 미정으로 유지한다. 기존 요구의 기술 형식 보완이며 명세 기능 버전은 바꾸지 않는다.

R1 작성 완료: 목록으로 남아 있던 8개 기능 요구를 기존 유스케이스의 동작·예외로 풀어 쓰고, 데이터·외부 인터페이스·공통 업무 규칙·비기능 검증·전체 추적표를 보완했다. 기존 기능 요구 24개와 비기능 요구 6개의 ID·최초 도입 버전·동작 의미를 유지한다. 문서 작성 완료가 미정 정책의 확정이나 앱 기능 완성을 뜻하지 않는다.

v0.2 변경: 사용자의 최신 설명에 따라 루틴 관찰·분석을 구체적인 계획 제안보다 앞에 둔다. 증량·유지·감량 선택과 큰 틀의 운동·식사·식비 방향을 반영한다. 세부 입력 방식, 관찰 기간, 분석 종료 조건은 아직 미정이다.
v0.3 변경: 앱 사용 기간 전체의 자동 수집, 사건 직후의 알림·고정 선택 UI, 3·7·15일 단위 분석과 매일의 계획 조정을 추가한다. 카드·건강 연동의 구체적인 구현 경로는 검증 후보이며 완전 자동화·항상 표시·즉시 동기화를 확약하지 않는다.

## 1. 문서 목적과 작성 방법

건강관리 튜터 앱이 사용자에게 제공해야 할 동작과 제약, 그 충족 여부를 확인할 기준을 정의한다.
기존 대화에서 명시된 의도와 이번에 구체화한 요구 후보를 구분한다. 문서 작성이 곧 사용자 승인 또는 구현 완료를 뜻하지 않는다.

작성 순서:

1. 목적·사용자·제품 범위
2. 핵심 사용 시나리오와 용어
3. 기능 요구와 업무 규칙
4. 데이터·외부 연동 요구
5. 비기능 요구와 측정 기준
6. 우선순위·수용 기준·추적 관계 검토

각 요구에는 ID, 근거, 상태, 동작과 수용 기준을 기록한다. 필요할 때 입력·출력·예외와 우선순위를 추가한다.
기능 추가·삭제나 동작·수용 기준의 의미 변경 시 다음 명세 버전과 변경일을 기록한다. 요구 ID의 최초 도입 버전은 유지하고, 영향받는 설계와 테스트를 연결한다.
검토 상태는 `의도 확인 / 상세 초안 / 상세 합의 / 보류`로 구분한다. 사용자 의도가 확인되어도 세부 동작이 합의된 것은 아니다.
수치·예외·기간 등 미정 사항이 남은 요구는 기준선 확정 전에 다시 검토한다.

이 문서는 특정 표준에 대한 적합성을 인증하는 문서가 아니다. 화면 배치, DB 제품, 클래스, 상태 관리 패키지는 후속 설계에서 정한다.

## 2. 제품 개요

### 2.1 목적 — 사용자 의도 확인

며칠간 사용자의 실제 루틴을 쉽게 기록하여 식사·가용 시간·지출 패턴을 파악하고, 선택한 일상 관리 방향에 맞는 실행 가능한 변경을 제안하는 개인 건강관리 튜터 앱을 만든다.
분석을 바탕으로 식사·운동·식비 계획을 제안하고 검토·승인·실행·변경·회고를 지원한다.
사용자 본인이 계속 사용하며 개선한다.

사용자는 체중 증량·유지·감량 중 방향을 선택하고 운동 지침과 식비 관리 방향을 정할 수 있어야 한다.
초기에는 입력하기 쉬운 생활 데이터를 쌓아 일상의 긍정적인 변화를 지원한다. 정밀한 체중·근육량 변화의 측정·추론은 후속 검토 대상으로 둔다.
이 결과는 앱이 제공할 기능과 구분하며, 특정 신체 변화나 비용 절감 결과를 보장하는 요구로 정의하지 않는다.
사용자 결과의 평가 기간과 측정 지표는 아직 미정이다.

### 2.2 사용자와 운영 환경

- 주 사용자: 앱을 직접 사용하고 개선 방향을 정하는 개인 1명
- 우선 플랫폼: Android
- 구현 제약: Flutter/Dart 사용
- 후속 목표: 집의 PC에서도 기록과 계획을 연동하여 사용. 방식과 개발 시기는 미정
- 언어·최소 Android 버전·지원 기기·접근성 범위: 상세 확인 필요
- 사용자 제공 시험 환경: 퀀텀3, Android 16·One UI 8.0, 갤럭시워치 8. 삼성페이·카드사 앱 결제 알림을 받는 환경. 실제 호환성은 아직 시험하지 않았다.

### 2.3 제품 범위 — 첫 배포 포함 여부는 별도 합의

| 영역 | 기존 대화의 의도·방향 | 현재 확인할 부분 |
|---|---|---|
| 루틴 관찰 | 구체적 식사·운동 추가에 앞서 며칠간 기존 일상을 파악 | 관찰 기간, 입력 방식, 필수 항목 |
| 지속 수집·자동화 | 관찰 종료 후에도 앱 사용 기간 전체에 걸쳐 수집. 카드·건강 연동으로 직접 입력 최소화 | 경로별 지원 범위·권한·누락 보완 |
| 능동적 상호작용 | 식사·지출·운동 직후 앱이 알림을 보내 고정 선택 UI로 응답 지원 | 잠금 상태 지원, 알림 피로·빈도·보안 |
| 분석 주기 | 3·7·15일 단위의 패턴 파악 | 누적·이동 기간, 실제 기록 충족 기준 |
| 일일 조정 | 매일 상호작용하며 새 정보로 계획을 조정 | 자동 적용 권한과 사용자 승인 범위 |
| 생활패턴 분석 | 무엇을 먹는지, 가용 시간·실제 지출을 확인하여 개선할 부분 도출 | 기록 부족 기준, 분석 표현, 사용자 확인 방식 |
| 관리 방향 선택 | 증량·유지·감량, 운동 지침, 식비 조절 방향 선택 | 지침 항목과 상충 목표의 우선순위 |
| 점진적 변경 | 관찰·선택한 방향에 맞는 실행 가능한 변화 제안 | 제안 개수·적용 기간·부담 수준 |
| 식사 | 요리할 메뉴·방법과 외식 대안 제안 | 식사 횟수, 상세 조리 정보, 식재료 입력 범위 |
| 운동 | 사용자가 정한 운동 방향과 가용 시간에 따른 실행 지원 | 첫 버전의 운동 지침 선택지·안내 수준 |
| 기간별 계획 | 월·주 단위 계획을 검토·승인한 뒤 조정 | 월간과 주간의 역할, 승인 단위 |
| 조리 환경 | 일반적인 한국 가정의 도구를 기본값으로 두고 없는 것을 제외 | 기본 목록 확정, 도구 부재 시 대체 동작 |
| 식비 | 사용자가 설정한 예산에 맞춘 계획 | 식비에 포함할 항목, 초과 시 처리 |
| 실행·기록·회고 | 실천에 따라 계획을 조정하는 흐름 | 입력 빈도·방법, 회고에 사용할 정보 |
| 장보기 | 계획에 필요한 목록과 재료 재사용은 기존 개발 제안 | 첫 버전 포함 여부와 승인 관계 |
| PC 연동 | 후속 목표 | 웹·설치형 앱·동기화 범위 |
| 신체 변화 측정 | 장기적으로 체중·근육량 변화도 파악하고 싶음 | 첫 단계 정밀 측정·자동 추론은 보류, 추후 수동 입력 여부 미정 |

전체 제품 방향과 첫 배포 범위를 구분한다. COCOMO 계산의 산정 범위는 검토용 후보이며 확정 요구가 아니다.
현재 첫 배포에서는 PC 연동을 후속으로 두는 방향이다. 다중 사용자·스토어 출시·워치 전용 앱·자동 영수증 인식 등은 요구 확정 전이다. 워치에서 생성된 건강 자료를 지원 경로로 가져오는 요구와 워치 전용 앱 개발을 구분한다.

### 2.4 시스템 경계와 관련 액터

| 액터 | 앱과의 상호작용 | 경계 |
|---|---|---|
| 사용자 | 방향·실행 여건 선택, 짧은 응답, 기록 정정, 분석·계획 검토·승인 | 주 사용자 1명. 관리자·의사·별도 코치는 현재 역할로 요구하지 않음 |
| 결제 자료 제공 시스템 | 지원 결제·정정·취소 자료 제공 | 알림 경로는 검증 후보. 금융 원장 전체 접근·과거 내역 복원을 전제하지 않음 |
| 건강·활동 자료 제공 시스템 | 허용된 걸음·운동 자료·변경 정보 제공 | 워치 → Samsung Health → Health Connect는 후보. 직접 워치 접근·즉시 동기화는 전제하지 않음 |
| Android 권한·알림 시스템 | 접근·게시 권한, 알림 전달·응답·잠금 상태 제약 | 앱의 노출 설정과 실제 OS 적용 상태를 구분 |
| 외부 AI 서비스(선택 시) | 허용된 자료에 따른 분석·제안·계획 초안 생성 | 공급자·전송 범위는 미정. 필수 외부 서비스로 확정하지 않음 |

시스템이 책임지는 범위는 앱의 수집·기록·분석·추천·계획 관리다. UI·내부 저장소·분석 모듈은 내부 구성 요소로 다루며 액터로 세지 않는다. 수집은 외부 사건으로 시작할 수 있고 분석·알림은 합의할 시각 도래로 시작할 수도 있다.

### 2.5 대표 제품 흐름과 상세 명세

관리 방향 선택·기존 루틴 관찰 → 근거·미상을 구분한 분석 → 변경 후보 선택 → 기간 계획 검토·승인 → 실행·기록 → 일일 조정·기간 점검으로 연결한다. 자동 수집은 전 과정에서 계속된다.

[유스케이스 목록](USE_CASES.md)은 목적 중심 18개·외부 연동 2개를 정의하며, [상세 명세](USE_CASE_SPECIFICATION.md)는 각 사례와 기존 전체 여정 2개에 개요·관련 액터·우선순위·선행 조건·후행 조건·이벤트 흐름·비기능 요구사항을 기록한다. 전체 여정은 하위 사례와 중복 집계하지 않는다.

## 3. 용어 초안

| 용어 | 의미 |
|---|---|
| 목표 | 사용자가 이루려는 건강·생활·예산상의 방향 |
| 관리 지침 | 목표에 접근하는 큰 틀의 생활·운동·식비 운영 방향. 선택지와 우선순위는 미정 |
| 관찰 기록 | 계획을 제안하기 전부터 수집하는 실제 식사·시간 사용·지출 등의 기록 |

### 4.2 입력하기 쉬운 관찰 데이터 — 개발 제안

아래는 수집할 정보 후보다. 모두 사용자가 직접 입력한다는 의미가 아니다. 자동 수집·미리 채우기·고정 선택을 우선하고, 사진·영수증·캘린더 등 추가 경로는 아직 선택하지 않았다.

### 4.3 UC-PLAN-001: 기간별 계획 검토 및 승인 — 상세 초안

6. 시스템이 승인 결과를 저장하고 해당 계획을 실행 안내의 기준으로 사용한다.

- 승인 취소: 기존 승인 계획을 유지한다.
- 저장 실패: 승인 완료로 표시하지 않고 기존 승인 계획을 유지한다.

승인 단위와 출력 범위가 미정이므로 이 시나리오는 아직 확정하지 않는다.

- 수용 기준 초안:
  - 변경 초안 검토·취소 중에는 기존 승인 계획을 유지한다.
  - 변경이 장보기·예상 지출 등에 미치는 영향을 해당 정보가 있을 때 확인할 수 있다.
  - 변경을 적용해도 이미 저장한 실제 식사·운동·결제 내역은 자동으로 바뀌지 않는다.
  - 변경 저장 실패 시 이전 실행 기준을 유지한다.
- 미정: 사소한 수정의 승인 방식, 변경 범위와 이력 보관, 이미 구매한 재료 처리

### 4.6 UC-CAPTURE-001: 사건 기반 자동 수집과 빠른 확인

- 액터: 사용자, 사용자가 허용한 결제·건강 데이터 출처
- 목적: 앱을 스스로 열어 일일이 적는 동작을 최소화하면서 사용 기간 내내 기록을 축적한다.
- 큰 방향은 사용자 의도 확인. 구체적 사건 처리와 권한·보완 흐름은 상세 초안이다.

1. 사용자가 연결 출처와 필요한 권한, 알림·잠금화면 표시 범위를 선택한다.
2. 시스템이 지원하는 결제 알림 또는 동기화된 건강 데이터를 가져온다.
3. 원본 출처와 시각을 보존하고 이미 가져온 자료와 중복·변경·취소 여부를 확인한다.
4. 바로 저장 가능한 자료는 수집하고, 식비 분류·먹은 음식·체감 등 필요한 정보만 알림으로 묻는다.
5. 사용자가 고정 버튼·짧은 답장 또는 알림에 연결된 짧은 입력 화면으로 보완한다.
6. 새 자료와 응답을 일일 요약·기간 분석·계획 변경 후보에 반영한다.

예외 초안: 권한 거부·회수, 지원하지 않는 알림 형식, 중복, 데이터 지연, 알림 차단·무응답, 재부팅·오프라인을 각각 처리한다. 실패나 미응답을 지출·활동 0이나 계획 변경 승인으로 간주하지 않는다.
최초 권한 설정과 복잡한 수정은 앱에서 이루어질 수 있으며 모든 상호작용을 잠금 해제 없이 처리한다고 보장하지 않는다.

#### REQ-INGEST-001: 지출 정보 가져오기

- 요구: 시스템은 사용자가 허용한 지원 결제 출처에서 지출 정보를 가져와 반복적인 금액·시각 입력을 줄여야 한다.
- 상태: 사용자 의도 확인, 상세 초안. 삼성페이·카드사 앱 알림 추출은 초기 검증 후보이며 직접 금융 API·내역 파일은 별도 후보
- 수용 기준 초안: 지원하는 가상 사건에서 추출한 필드를 미리 채우고 출처와 확인 상태를 표시한다. 읽을 수 없는 필드는 만들어내지 않는다.
- 결제 기록만으로 먹은 음식·양·식사 여부를 확정하지 않는다. 자동 분류·집계 허용 범위는 Q-14에서 결정한다.

#### REQ-INGEST-002: 건강·활동 기록 가져오기

- 요구: 시스템은 사용자 허용 범위의 삼성 헬스·갤럭시워치 데이터에서 지원하는 활동 기록을 가져와 재입력을 줄여야 한다.
- 상태: 사용자 의도 확인, 상세 초안. Health Connect 우선 검증 후보
- 수용 기준 초안: 지원되는 걸음·운동 자료의 출처·관측 시각·가져온 시각·동기화 상태를 확인할 수 있고 같은 자료의 재수집으로 중복 증가하지 않는다.
- 동기화 미완료를 '운동하지 않음'으로 해석하지 않는다. 정확히 가져온 기록마다 수동 재확인을 필수로 요구하지 않는 안을 제안한다.

#### REQ-INGEST-003: 권한과 지속 수집 상태

- 요구: 시스템은 출처별 연결·권한·마지막 수집·실패 상태를 관리하고, 초기 관찰 이후에도 허용한 자동 수집을 이어가야 한다.
- 상태: 지속 수집은 사용자 의도 확인, 권한·재시도 상세는 개발 제안
- 수용 기준 초안: 권한 회수 시 해당 수집이 중단되며, 권한 없는 자료를 수집 완료로 표시하지 않는다. 재연결 시 허용된 범위의 보완과 중복 방지를 적용한다.

#### REQ-INGEST-004: 중복·정정·취소 처리

- 요구: 시스템은 동일 사건의 반복 도착과 출처 간 중복 후보를 다루고, 정정·취소를 단순 신규 기록과 구분해야 한다.
- 상태: 자동 수집의 정확성을 위한 개발 제안
- 수용 기준 초안: 같은 원본 ID의 재수집은 집계를 증가시키지 않는다. 가상 결제가 삼성페이와 카드사 앱 양쪽에서 들어온 경우 두 건으로 확정하지 않고 중복 여부를 처리한다.
- 거래·활동의 출처 간 동일성 기준과 환불 규칙은 미정이며 합칠 근거가 부족하면 불확실 상태로 둔다.

#### REQ-INTERACT-001: 앱이 먼저 제안하는 알림

- 요구: 시스템은 지원 사건 도착이나 동의한 시점에 기록 보완·실행·계획 변경을 위한 알림을 보내야 한다.
- 상태: 사용자 의도 확인, 상세 초안
- 수용 기준 초안: 사건 기반 확인이나 정해진 보완 시점으로부터 관련 기록·행동에 연결되는 알림을 만들고, 처리한 사건에 대해 같은 질문을 반복하지 않는다.
- 조용한 시간·빈도·묶음 확인·미루기는 설정 가능한 방향을 제안한다. 알림이 차단되면 미처리 항목으로 보존하며 응답을 대신 생성하지 않는다.
- 식사·운동 직후라는 희망 시점과 데이터가 실제 도착한 시점을 구분한다. 감지할 수 없는 사건을 이미 감지했다고 표시하지 않는다.

#### REQ-INTERACT-002: 고정 선택과 잠금화면 진입점

- 요구: 시스템은 짧은 기록·확인을 고정 선택 UI와 지원되는 알림 동작으로 처리하여 전체 앱을 찾아 여는 부담을 낮춰야 한다.
- 상태: 사용자 의도 확인, 상세 초안
- 수용 기준 초안: 분류·실행 여부 등 합의한 대표 과제를 알림 동작으로 처리하거나, 해당 항목이 미리 채워진 짧은 입력 화면으로 바로 연결한다. 응답이 저장됐는지 알 수 있어야 한다.
- 잠금화면 표시는 사용자가 허용한 범위와 OS 제약을 따른다. 영구 표시·전체 잠금화면 대체·항상 인증 없이 처리하는 것을 수용 기준으로 두지 않는다.

#### REQ-ROUTINE-004: 3·7·15일 분석과 계속되는 관찰

- 요구: 시스템은 사용 기간 동안 수집을 계속하면서 3일·7일·15일 단위로 생활패턴 요약을 지원해야 한다.
- 상태: 사용자 의도 확인, 계산·실행 규칙은 상세 초안
- 수용 기준 초안: 각 분석의 대상 기간·실제 수집 범위·미상 자료를 구분하여 조회할 수 있고 초기 관찰 단계가 끝나도 데이터 수집이 중단되지 않는다.
- 각 기간만 지나면 패턴이 통계적으로 확정된다고 표현하지 않는다. 누적·이동 기간, 기록일·달력일, 분석 개시 조건은 Q-08에서 결정한다.

#### REQ-PLAN-004: 매일 상호작용에 따른 계획 조정

- 요구: 시스템은 매일 새로 수집한 자료와 사용자 응답을 바탕으로 필요한 계획 변경을 제안할 수 있어야 한다.
- 상태: 사용자 의도 확인, 자동 적용 권한과 승인 방식은 미정
- 수용 기준 초안: 변경 이유·범위·영향을 확인할 수 있고 거절·무응답 중에는 기존 승인 계획을 유지한다. 실제 기록을 계획에 맞게 자동 수정하지 않는다.
- 모든 미세 조정마다 별도 대화가 필요한지, 어떤 변경을 사전 위임할지는 Q-06에서 결정한다. 알림 동작으로 간단히 승인하는 안을 검토한다.

### REQ-PROFILE-001: 조리도구 기본값 확인

- 근거·상태: 사용자의 기본 목록에서 없는 도구를 제외하자는 요청. 사용자 의도 확인, 실제 기본 목록·확인 시점은 미정.
- 입력·결과: 수정 가능한 일반 한국 가정의 도구 기본값에서 없는 것을 제외하고 추천에 사용할 조건으로 저장한다. 식재료는 도구와 별도로 다룬다.
- 수용 기준 초안: 제외한 도구가 필요한 메뉴를 그대로 실행 가능한 것으로 제시하지 않는지 확인한다. 기본 가정을 사용자가 실제 보유 확인한 값과 구분한다.
- 예외·미정: 저장 취소·실패는 완료로 표시하지 않는다. 필수 확인·대체 도구 안내·재료 상세 관리는 Q-02/Q-09에서 정한다.
- 연결: UC-PROFILE-001, UC-CHANGE-001.

### REQ-PLAN-003: 관찰·관리 방향에 근거한 기간 계획 생성

- 근거·상태: 사용자 요청의 기간 계획과 관찰 우선 흐름. 사용자 의도 확인, 상세 초안.
- 입력·결과: 관찰·분석, 선택한 변경·관리 방향, 기간·예산·알려진 실행 여건을 사용해 검토할 초안과 예상 지출·주요 가정을 제시한다.
- 수용 기준 초안: 첫 제안은 기존 루틴 관찰·변경 검토 뒤에 이어지고, 사용한 근거·조건과 미상·추정을 확인할 수 있다. 생성된 초안만으로 실행 기준을 전환하지 않는다.
- 예외·미정: 정보 부족·생성 실패를 표시하며 기존 승인 계획·실제 기록을 유지한다. 월·주 관계·승인 묶음·필수 입력·출력은 Q-01/Q-08/Q-09 미정.
- 연결: UC-PLAN-001, REQ-PLAN-001, REQ-CHANGE-001.

### REQ-MEAL-001: 조리 실행 안내

- 근거·상태: 요리할 메뉴·방법 등 실행 가능한 지침을 받고 싶다는 사용자 요청. 의도 확인, 안내 상세는 초안.
- 입력·결과: 대상 요리와 알려진 조리 여건에 따라 필요한 재료·조리 방법을 보여준다.
- 수용 기준 초안: 대상 요리의 재료·단계를 확인할 수 있다. 확인된 도구·시간 제약과 충돌하는 조건을 충족된 것으로 안내하지 않는다. 미상 재료 보유·비용은 확정값으로 표시하지 않는다.
- 예외·미정: 안내 조회·생성 실패는 구분하고 실제 식사 완료·지출로 기록하지 않는다. 상세 안내 수준·보유 재료 확인 범위는 후속 검토다.
- 연결: UC-MEAL-001, UC-PROFILE-001.

### REQ-MEAL-002: 조리가 어려울 때 식사 대안 제시

- 근거·상태: 요리가 어려우면 어떤 음식을 먹을지 추천받고 싶다는 사용자 요청. 의도 확인, 상세 초안.
- 입력·결과: 현재 시간·예산·알려진 제약을 사용해 외식 등 식사 후보와 선택 이유를 제시한다.
- 수용 기준 초안: 알려진 제약과 후보의 관계를 확인하고 추정 비용·미상 정보를 구분할 수 있다. 대안 조회·선택만으로 승인 계획이나 실제 섭취 기록을 바꾸지 않는다.
- 예외·미정: 적합한 후보가 없거나 생성에 실패하면 성공으로 표시하지 않는다. 실시간 가격·영업 정보·주문 연동은 확정 범위가 아니다.
- 연결: UC-MEAL-002. 승인 계획의 변경은 UC-PLAN-002에서 검토한다.

### REQ-EXERCISE-001: 지침·시간에 맞는 운동 수행 안내

- 근거·상태: 선택한 운동 지침으로 생활 변화를 돕고 싶다는 사용자 요청. 의도 확인, 안내 수준은 Q-04/Q-10 미정.
- 입력·결과: 선택한 지침과 확인된 시간 여건을 사용해 합의할 수준의 운동 계획·수행 정보를 제시한다.
- 수용 기준 초안: 안내에 사용한 지침·시간 조건을 확인할 수 있다. 사용할 수 없다고 확인한 시간을 가용 시간으로 쓰지 않으며 안내 조회를 운동 완료로 기록하지 않는다.
- 예외·미정: 조건 부족·미지원 안내 범위·생성 실패를 표시한다. 종류·강도·필수 제약은 미정이고 정밀 신체 변화 측정·의료적 처방은 범위에 넣지 않는다.
- 연결: UC-EXERCISE-001, UC-ACTIVITY-001, UC-ACTION-001.

### REQ-RECORD-001: 실제 기록과 계획의 구분

- 근거·상태: 관찰·실행 중 쉬운 기록과 계속되는 조정이라는 사용자 방향. 의도 확인, 입력 문항·필수 필드는 초안.
- 입력·결과: 실제 식사·활동·지출과 필요한 짧은 피드백을 계획 유무에 관계없이 기록·조회·보완한다.
- 수용 기준 초안: 승인 계획 없이 실제 기록을 남길 수 있고, 계획 변경 전후에도 이미 성공 저장한 실제 기록은 보존된다. 미입력·미응답을 미수행·0원으로 대신 입력하지 않는다.
- 예외·미정: 반복 응답·자동 수집과의 중복을 구분하고 저장 실패를 성공으로 표시하지 않는다. 실제 기록 정정과 분석 해석 정정은 별도 동작이다.
- 연결: UC-RECORD-001, UC-ACTION-001, UC-INTERACT-002.

### REQ-BUDGET-001: 실제 식비의 중복 합산 방지

- 근거·상태: 장보기 구매와 끼니 원가를 구분하자는 기존 개발 제안. 상세 초안.
- 입력·결과: 실제 결제·예상 비용·미분류 및 미상 범위를 구분하여 기간 지출을 정리한다.
- 수용 기준 초안: 한 번 구매한 재료를 여러 끼에 사용해도 구매 결제액과 매 끼니의 추정 원가를 실제 식비에 중복 합산하지 않는다. 같은 사건의 반복 수집으로 집계를 늘리지 않는다.
- 예외·미정: 식비 포함 항목·혼합 구매·중복 후보·취소·환불·월/주 경계와 예산 초과 처리는 Q-01/Q-03/Q-14에서 정한다. 기록 누락을 실제 지출 0원으로 처리하지 않는다.
- 연결: UC-BUDGET-001, UC-EXPENSE-001, REQ-INGEST-004.

### REQ-REVIEW-001: 기간별 실행·지출 점검

- 근거·상태: 실제 결과를 다음 계획에 반영하자는 기존 회고 흐름의 개발 제안. 상세 초안.
- 입력·결과: 기간의 실제 수집 범위·실행·지출·확인된 부담을 정리하여 다음 검토에 사용할 근거를 제시한다. 관련 계획이 있을 때는 계획 대비 결과를 구분한다.
- 수용 기준 초안: 정리한 결과의 기간·기록 범위·미상 정보를 확인하고 다음 분석·변경 검토로 연결할 수 있다. 기록량 증가만으로 생활 개선·신체 변화가 입증됐다고 판단하지 않는다.
- 예외·미정: 정보 부족·조회/요약 실패를 표시하며 실제 기록·승인 계획을 유지한다. 지표·평가 기간·다음 계획 반영 방식은 미정이다.
- 연결: UC-REVIEW-001, UC-ANALYSIS-001, UC-PLAN-002.

## 6. 데이터·외부 연동 요구 — 범위 확인 필요

데이터 후보: 증량·유지·감량 방향, 관리 지침, 사용자 조건, 날짜별 관찰 기록, 사용자가 확인한 가용 시간, 분석의 대상 기간·근거·미상 정보, 변경 후보와 선택, 조리도구, 보유 재료, 계획·변경 이력, 실제 실행·결제 내역.
분석 결과를 관찰 사실과 구분하며, 지출 금액의 미상·추정·실제 구분을 유지한다. 분석·제안이 참조한 기록과 목표의 기준을 추적하는 방안을 설계에서 검토한다.
체중·근육량의 정밀 측정과 자동 변화 추론은 후속 범위로 둔다. 수동 신체 수치 기록을 추가할지, 언제 할지는 아직 정하지 않았다.
보유 재료의 세부 수량·유통기한까지 관리할지는 미정이다.
외부 AI로 보낼 정보, 저장 위치·기간, 삭제 범위, 오프라인 기능, AI 제공자·실시간 가격 조회 여부는 미정이다.
추가 데이터 후보: 연결 출처·권한 상태, 원본 ID·수정 상태·관측/수집 시각, 분류·확인 상태, 알림 질문·응답·처리 상태, 분석 창과 마지막 분석 기준.
알림·금융·건강 원문 전체를 AI에 전송하는 것을 기본 가정으로 두지 않는다. 필요한 항목의 범위와 로컬 처리·보관 방식을 설계에서 결정한다.
연동·알림의 공식 근거와 제약은 [데이터 연동 검토](INTEGRATION_OPTIONS.md)에 기록한다. 구체적 구현 경로는 요구와 분리하여 검증한다.
개인 건강·생활 정보나 비밀키를 저장소 문서·예시·테스트 데이터에 기록하지 않는다. 검증에는 가상 데이터를 사용한다.

| 승인 계획·이력 | 승인한 내용·버전·적용 범위, 저장 성공 상태 | 승인·저장 성공한 기준으로 실행. 이전 실제 기록은 재작성하지 않음 |
| 실행·회고 정보 | 실제 수행 여부·필요한 짧은 피드백, 기간별 집계·미상 | 무응답과 미수행을 구분. 입력량 증가만으로 개선을 판단하지 않음 |

보관 기간·삭제·외부 전송·오프라인 처리는 Q-07, 분석 기간 경계와 자료 충족은 Q-08, 시간·금액 집계의 자세한 규칙은 Q-01/Q-03/Q-14와 연결한다. 현재 정보가 없는 값을 자동으로 만들어 필수 필드를 채우지 않는다.

## 10. 작성 완료 범위와 다음 단계

| 항목 | 현재 상태 |
|---|---|
| 목적·범위·액터·용어·전체 제품 흐름 | 작성 완료. 첫 배포 포함 범위는 별도 결정 |
