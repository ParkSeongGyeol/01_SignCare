# 소프트웨어 공학 기반 개발 절차

상태: 프로젝트에 적용할 절차 제안. 세부 설계는 미확정.
기준일: 2026-10-17 (Asia/Seoul)

사용자는 소프트웨어 공학 책의 내용을 연습하려는 목적을 명시했다. 실제 산정 과정과 모델을 남기는 것을 개발의 일부로 다룬다.
현재 계획 단계는 [COCOMO II 및 일정 계획](planning/PLAN.md)에 정리한다. 사용자 요청에 따라 이번 타당성 분석과 별도 위험분석은 생략한다.
현재 제품 요구는 [요구분석명세서 v0.3](REQUIREMENTS_SPECIFICATION.md)를 우선한다. 관찰·실행 전 기간에 자동 수집과 짧은 알림 응답을 사용하고 루틴 분석 후 변경을 제안한다. 연동·잠금 상태의 기술 경계는 [공식 문서 검토](INTEGRATION_OPTIONS.md)를 참고하되 실기로 검증해야 한다.
현재는 [기능·상호작용 설계 D0.1](design/DESIGN.md)을 작성한 단계다. 기능·요구 변경 시 [변경 이력](REQUIREMENTS_CHANGELOG.md)에 버전·날짜·영향 ID를 남기며, 설계의 세부화 자체를 새 기능 도입으로 취급하지 않는다.
2026-10-18에는 분석 추적 관계를 보완해 [유스케이스 목록 UC0.1](USE_CASES.md)을 작성했다. 목록·상세 시나리오·설계는 반복해서 보완하며, 기존 요구를 목적별로 분류한 것만으로 명세 기능 버전을 올리지는 않는다.
상세 작성 형식은 사용자가 지정한 개요·관련 액터·우선순위·선행 조건·후행 조건·이벤트 흐름·비기능 요구사항이다. [유스케이스 명세서 UCS0.1](USE_CASE_SPECIFICATION.md)에 적용했으며, 이벤트 흐름에는 트리거·기본·대안/예외를, 후행 조건에는 성공·실패/중단 시 보존 상태를 구분한다.
요구분석명세서는 [v0.3/R1 작성 완료·검토본](REQUIREMENTS_SPECIFICATION.md)으로 정리했다. 기능 24개·비기능 6개와 데이터·외부 인터페이스·업무 규칙·검증 후보의 추적표를 포함한다. 문서 작성은 완료했으며, Q-01~Q-14 정책·품질 수치·첫 배포 범위·기준선은 후속 검토한다.

## 1. 절차를 이해하는 방법

사용자가 제시한 순서를 학습과 산출물의 틀로 따른다.

**UML → 계획 → 요구분석 → 설계 → 아키텍처·클래스 설계 → 디자인 패턴 → 구현 → 테스트 → 품질 → 프로젝트 관리**

다만 다음을 함께 적용한다.

- UML은 별도의 개발 생명주기가 아니라 시스템을 표현하는 언어다. 첫 단계에서는 가벼운 개념 모델만 만들고, 요구와 설계가 구체화되면 해당 UML도 수정한다.
- 한 번의 순회로 모든 것을 확정하지 않는다. 작은 기능 단위로 요구부터 검증까지 반복한다.
- 테스트의 기대 결과는 요구분석부터 정한다. 품질과 프로젝트 관리는 처음부터 병행한다.
- 단계 완료 기준은 산출물의 검토 기준이다. 사소한 문서 수정까지 매번 별도 사용자 승인을 요구하지 않는다.
- 계획 승인이라는 앱 기능의 사용자 승인과 개발 과정에서의 설계 논의는 구분한다.

## 2. 단계별 질문과 산출물

| 단계 | 스스로 물어볼 질문 | 이 앱에서 만들 산출물 | 다음으로 진행할 근거 |
|---|---|---|---|
| 1. UML | 누가 어떤 일을 하며, 핵심 상태는 어떻게 바뀌는가? | 유스케이스 목록, 계획 승인 상태도, 핵심 상호작용 초안 | 제안·수정·승인·실행 흐름을 설명할 수 있음 |
| 2. 계획 | 무엇을 만들며 비용·공수·일정을 어떻게 산정하는가? | 범위, COCOMO II 산정, 작업 분해, 의존관계, 네트워크·간트 차트 | 가정·계산 과정·주공정·자원 용량과 완료 기준이 분명함 |
| 3. 요구분석 | 무엇을 해야 하며 어떻게 성공을 확인하는가? | 기능·비기능 요구 ID, 수용 기준, 용어, 미정 질문 | 입력·결과·예외가 구체적이고 시험 가능함 |
| 4. 설계 | 사용자가 어떤 화면과 행동으로 목적을 이루는가? | 화면 흐름, 와이어프레임, 입력·오류·오프라인 상태, 데이터 개념 | 정상 및 실패 흐름을 따라갈 수 있음 |
| 5. 아키텍처·클래스 설계 | 책임과 의존성을 어디에 둘 것인가? | 구성도, 책임표, 주요 클래스·시퀀스, 데이터 계약, 결정 기록 | 화면·계획 규칙·저장·외부 호출의 책임이 분리됨 |
| 6. 디자인 패턴 | 반복되는 어떤 문제를 어떤 구조로 해결할 것인가? | 채택·보류한 패턴과 이유 | 실제 문제와 이점이 설명되며 불필요한 구조가 없음 |
| 7. 구현 | 가장 작은 사용 흐름을 끝까지 작동시키려면? | Flutter 코드, 저장·연결 구현, 실행 안내 | 대상 기기에서 해당 흐름을 실행할 수 있음 |
| 8. 테스트 | 의도한 규칙과 예외 처리가 실제로 지켜지는가? | 단위·위젯·통합 테스트, 실제 기기 확인 결과 | 수용 기준을 충족하고 중요한 실패가 해결됨 |
| 9. 품질 | 지속적으로 믿고 쓸 수 있는가? | 정확성·사용성·복구·보안·유지보수 점검과 개선 기록 | 데이터 손상 등 중대한 결함이 없고 제한이 명시됨 |
| 10. 프로젝트 관리 | 지금 무엇이 완료됐고 무엇이 막혀 있는가? | 상태표, 작업 목록, 변경·결정·위험 기록, 다음 목표 | 다음 작업과 완료 근거를 다른 세션도 이해함 |

## 3. 요구부터 테스트까지 연결하는 예

아래는 요구분석 때 검토할 초안이며 사용자 확정 명세가 아니다.
계획 승인 예시는 관찰·분석 후의 하위 흐름이다. 최초 사용은 루틴을 먼저 파악하는 UC-ROUTINE-001부터 다룬다.

**REQ-PLAN-001: 계획 승인**

- 사용자는 주간 계획의 식사·운동·장보기·예상 지출을 검토하고 승인할 수 있다.
- AI가 생성한 내용은 우선 초안으로 보관한다.
- 승인 동작이 성공하면 승인한 버전이 실행 화면의 기준이 된다.

**REQ-PLAN-002: 승인된 계획의 수정**

- 일정 변경을 요청하면 기존 계획을 기준으로 변경 초안을 제안한다.
- 변경 영향과 차이를 확인할 수 있다.
- 새 버전을 승인하기 전까지 기존 승인 버전을 유지한다.
- 완료 기록과 실제 결제 내역은 계획 재생성만으로 바꾸지 않는다.

REQ-PLAN-002의 수용 기준 예:

> 승인된 주간 계획이 있을 때 사용자가 수요일 저녁을 외식으로 바꾸면, 앱은 변경 초안과 장보기·예상 지출의 변화를 보여준다. 적용하기 전에는 기존 계획을 유지하고, 적용 후에는 새 버전을 사용한다. 이미 기록된 결제 내역은 그대로 남는다.

| 요구 | UML·설계 | 구현 후보 | 검증 예 |
|---|---|---|---|
| REQ-ROUTINE-001/002 | 루틴 관찰·분석 시퀀스 | 관찰 기록·기간 요약·근거 표시 | 계획 없이 기록 가능, 누락을 0으로 해석하지 않음 |
| REQ-PLAN-001 | 승인 시퀀스, 상태도 | 승인 처리와 저장 | 검토한 버전만 승인되고 재실행 후에도 유지됨 |
| REQ-PLAN-002 | 변경 시퀀스, 버전 관계 | 변경 초안과 버전 전환 | 취소·실패 시 기존 버전 유지, 기록 보존 |
| REQ-BUDGET-001 | 지출 데이터 관계 | 예산·지출 계산 | 장보기 결제와 끼니 원가를 중복 합산하지 않음 |

금액은 원 단위 정수, 기간은 명확한 날짜 경계로 다루는 방안을 검토한다. 월말, 주간이 두 달에 걸치는 경우, 환불 처리 등의 규칙은 요구분석에서 정한다.

## 4. UML을 언제 사용하는가

- 요구분석: 유스케이스로 사용자 목적과 시스템 경계를 표현한다.
- 업무 흐름: 활동도로 계획 제안, 검토, 수정, 승인 단계를 표현한다.
- 상태 규칙: 상태도로 초안, 승인, 대체된 버전의 전이를 표현한다.
- 동작 설계: 시퀀스도로 UI, 계획 처리, 저장, AI 사이의 호출과 실패 흐름을 표현한다.
- 구조 설계: 클래스도로 핵심 개념의 책임과 관계를 표현한다.
- 아키텍처: 컴포넌트·배포 관점에서 모바일, 로컬 저장소, 서버, AI 경계를 표현한다.

처음부터 모든 다이어그램을 작성하지 않는다. 오해나 복잡성을 줄이는 모델부터 작성한다.
현재 초기 모델은 [UML.md](UML.md)에 있다. Mermaid 표기 중 시퀀스·상태·클래스 다이어그램을 사용하며, 설명용 목록을 정식 UML 유스케이스 도형으로 오인하지 않는다.

## 5. Flutter 아키텍처의 출발 후보

아래는 요구분석 후 검토할 제안이며 확정하지 않았다.

- View: 화면 표시와 사용자 입력
- ViewModel: 화면 상태와 사용자 명령 처리
- 계획 규칙: 승인·변경·금액 계산처럼 중요한 규칙. 복잡해질 때 별도 도메인 로직으로 분리
- Repository: 계획·기록 데이터 접근 경계
- Service/Adapter: 로컬 DB, 네트워크, 외부 AI 등의 실제 입출력

첫 단계부터 많은 추상 계층과 모든 클래스의 인터페이스를 만들지 않는다.
View 안에서 직접 AI를 호출하거나 승인 규칙을 처리하지 않도록 책임을 나누는 것이 우선이다.
DB, 서버, 상태 관리, 의존성 주입 패키지는 요구와 첫 사용 흐름을 정한 뒤 선택한다.
AI 비밀키는 배포 앱에 포함하지 않는 방향으로 설계하고 서버 경계를 검토한다.

후보 패턴:

| 후보 | 해결하려는 문제 | 도입 판단 |
|---|---|---|
| MVVM | 화면 표시와 화면 동작·상태 분리 | Flutter 공식 가이드를 참고한 출발 후보 |
| Repository | 화면이 저장 방식에 묶이는 문제 | 저장·동기화·테스트 대체가 필요할 때 |
| 의존성 주입 | 실제 저장소와 테스트용 구현을 교체하기 어려움 | 처음에는 생성자 전달로 충분한지 검토 |
| Adapter | AI 공급자별 응답 형식 차이 | 실제 AI 연동 시 검토 |
| Strategy | 여러 계획 생성 방식을 교체해야 함 | 실제 복수 전략이 생기기 전에는 보류 |

클래스명이나 패턴 수가 설계 품질을 증명하지 않는다. 책임이 분명하고 변경과 테스트가 쉬운지로 판단한다.

## 6. 테스트와 품질

우선 검증할 위험:

1. 승인하지 않은 계획이 실행 계획으로 바뀜
2. 변경 또는 저장 실패로 기존 계획과 기록이 사라짐
3. 구매 금액과 끼니 원가의 중복 합산
4. AI가 없는 도구·재료 또는 잘못된 데이터 형식으로 실행 불가능한 계획을 만듦
5. 재실행 후 데이터가 사라지거나 중복 생성됨

테스트 구성:

- 단위 테스트: 예산 계산, 기간 경계, 승인·변경 규칙
- 위젯 테스트: 초안 표시, 변경 비교, 승인·취소·오류 상태
- 통합 테스트: 계획 제안부터 승인·저장·재실행·변경까지의 흐름
- 실제 Android 확인: 입력 편의, 가독성, 접근성, 네트워크 실패 시 동작

AI 문장 자체를 고정값으로 비교하기보다 응답 구조, 제약 준수, 처리 실패 시 복구를 검증한다. AI 기능 평가와 앱의 결정적 규칙 테스트를 구분한다.
분석·테스트 명령은 프로젝트가 만들어진 후 `flutter analyze`, `flutter test` 등을 적용한다. 현재 실행된 결과는 없다.

사용자 결과와 소프트웨어 품질도 구분한다.

- 사용자 결과: 실제 식비, 실천율, 몸 상태·운동 수행 등의 추세. 상세 지표는 미정
- 소프트웨어 품질: 기록 정확성, 저장 신뢰성, 사용성, 반응성, 개인정보 처리, 수정 용이성

## 7. 작은 기능 단위의 반복

첫 구현 후보는 다음 흐름이다.

> 가상 결제·운동 사건을 수신하고 → 중복 없이 저장하고 → 부족한 정보만 알림·짧은 UI로 확인하고 → 루틴 요약·개선 후보 검토 흐름으로 연결한다.

처음에는 가상 기록·예시 분석으로 관찰 데이터·미상 정보·해석을 구분하는 흐름을 검증할 수 있다.
실제 Health Connect·결제 알림·잠금 상태는 별도의 작은 기기 시험으로 확인한다. 외부 동기화·권한·알림 제약을 가상 데이터 시험만으로 검증했다고 기록하지 않는다.
계획 승인·저장 예시는 이후 하위 흐름으로 유지한다. 실제 AI, 재료 재사용, 운동 개인화, 회고, PC 연동은 요구 범위에 따라 검토한다.
첫 버전의 정확한 포함 범위는 계획 단계에서 정한다.

매 반복에서는 요구 ID, 관련 설계, 코드, 검증 근거, 남은 제한을 함께 갱신한다.
일정 추정은 SDK 환경과 작은 실행 경로를 확인한 뒤 작성한다.
