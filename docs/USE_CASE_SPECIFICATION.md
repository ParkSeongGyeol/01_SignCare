# 유스케이스 명세서

문서 버전: UCS0.1 / 작성·갱신: 2026-10-18 (Asia/Seoul)
참조: [요구분석명세서 v0.3](REQUIREMENTS_SPECIFICATION.md), [유스케이스 목록 UC0.1](USE_CASES.md), [설계 D0.1](design/DESIGN.md)
상태: 공동 검토용 상세 초안. 사용자 의도가 확인된 기능과 개발 제안을 구분한다. 구현·테스트 완료 또는 첫 배포 범위 확정을 뜻하지 않는다.

기존 목록의 20개 사례와 기존 전체 여정 2개를 모두 요청한 일곱 항목으로 기술한다. 전체 여정은 하위 사례를 연결하는 요약이며 신규 기능으로 중복 집계하지 않는다. 기존 요구·설계의 동작을 풀어 쓰는 문서화로, 명세 v0.3·설계 D0.1·목록 UC0.1을 유지한다. 새로운 기능이나 수용 기준을 결정하면 [변경 이력](REQUIREMENTS_CHANGELOG.md)과 요구 버전을 함께 갱신한다.

## 작성 규칙

각 사례는 **개요 → 관련 액터 → 우선순위 → 선행 조건 → 후행 조건 → 이벤트 흐름 → 비기능 요구사항** 순서로 작성한다.

- 개요에는 목적·연결 요구·합의 상태·미정 질문을 기록한다. Q 번호는 요구분석명세서의 질문 ID다.
- 선행 조건은 사례를 시작하기 전에 성립하는 상태다. 시작 계기인 트리거는 이벤트 흐름에 별도로 적는다.
- 후행 조건은 성공했을 때와 실패·취소·중단했을 때로 나눈다. 부분 수집·부분 확인은 완전한 완료와 구분한다.
- 기본 흐름의 번호는 해당 사례 안의 순서다. 대안·예외는 분기 지점과 처리 결과를 함께 적는다.
- 우선순위는 **상세 검토·구체화 순서의 개발 제안**이다. P1(높음)은 관찰·수집·분석·승인 핵심 흐름과 데이터·권한 보호, P2(보통)는 실행 지원·해석 보완·회고의 상세 흐름이다. P2도 현재 제품 방향에 포함되며 첫 출시 제외를 뜻하지 않는다. 구현 순서·출시 범위는 별도 결정한다.
- 앱 내부의 저장소·분석 모듈은 액터가 아니다. 외부 AI는 채택할 경우에만 보조 액터로 참여하며, 외부 전송 동의·범위·연결 조건은 Q-07에서 정한다.
- 실패 시 '기존 데이터 유지'는 이미 성공적으로 저장한 자료를 뜻한다. 저장하지 못한 입력의 복구·재시도·오프라인 보장 범위는 미정이다.
- 각 사례의 흐름은 상세 초안이다. 미정 항목의 자동 처리·기본값·숫자를 확정한 것으로 해석하지 않는다.

## UC-GOAL-001: 체중·생활·식비 관리 방향 정하기

### 개요

증량·유지·감량과 큰 틀의 운동·식사·식비 방향, 목표 예산을 정하여 이후 분석·제안의 기준으로 삼는다. 연결 요구: REQ-GOAL-001, REQ-GOAL-002, REQ-PLAN-003. 사용자 방향은 확인됐으며 지침 선택지·상충 목표·설정 시점·식비 범위는 Q-02/Q-03/Q-10에서 결정한다.

### 관련 액터

- 주 액터: 사용자.
- 외부 AI를 사용하는 제안 단계는 후속 사례에 해당하며 이 설정 동작의 필수 액터가 아니다.

### 우선순위

P1(높음·제안). 관찰 결과를 어떤 방향으로 해석하고 변경할지 정하는 기준이다.

### 선행 조건

- 신규 설정 또는 기존 방향의 재검토가 가능한 상태다. 관찰·승인 계획·신체 측정값은 필수 전제가 아니다.

### 후행 조건

- 성공: 저장한 방향·예산 조건을 조회하고 이후 제안에서 사용한 기준으로 확인할 수 있다.
- 취소·실패: 기존 저장값을 유지하고 저장 완료로 표시하지 않는다. 방향 수정만으로 승인 계획이나 실제 기록을 바꾸지 않는다.

### 이벤트 흐름

트리거: 사용자가 최초 방향 설정 또는 기존 방향 변경을 요청한다.

기본 흐름:

1. 시스템이 현재 선택값과 설정할 항목을 제시한다.
2. 사용자가 체중 방향과 합의할 지침·예산 조건을 선택한다.
3. 시스템이 저장할 내용을 제시하고 사용자 입력을 저장한다.
4. 시스템이 저장 결과와 현재 방향을 보여준다.

대안·예외:

- 2단계에서 지침 선택지·예산 범위가 정해지지 않은 부분은 미정 사항으로 남긴다. 이 초안으로 임의의 기본값·충돌 해결 규칙을 확정하지 않는다.
- 3단계에서 취소하거나 저장에 실패하면 기존 값을 유지한다.
- 저장한 방향 때문에 기존 계획을 바꿀 필요가 있으면 UC-PLAN-002의 변경 검토로 연결한다. 자동 변경 위임 범위는 미정이다.

### 비기능 요구사항

- NFR-DATA-001: 성공 저장한 방향·예산 조건이 재실행 후 조회되는지 확인한다.
- NFR-USABILITY-001: 초기 필수 입력 수·선택 조작 수를 측정한다. 한 번에 모든 생활 조건을 입력받지 않는 방향이다.
- NFR-PRIVACY-001: 목표·예산의 보관과 후속 외부 전송 범위는 Q-07의 정책에 연결한다.

## UC-PROFILE-001: 조리·운동에 사용할 실행 여건 확인하기

### 개요

조리도구와 실제 가용 시간 등 알려진 실행 여건을 확인하여 실행 불가능한 추천을 줄인다. 연결 요구: REQ-PROFILE-001, REQ-ROUTINE-001, REQ-ROUTINE-003. 도구를 기본값에서 제외하는 방식은 사용자 방향, 가용 시간 확인·정정 방식은 개발 제안이다. 기본 목록·필수 확인 시점은 Q-02/Q-09에서 결정한다.

### 관련 액터

- 주 액터: 사용자. 캘린더 자동 연동은 현재 전제로 두지 않는다.

### 우선순위

P2(보통·제안). 추천의 실행 여건을 구체화한다. 세부 목록 전체를 초기 진입의 필수 설문으로 만들지는 않는다.

### 선행 조건

- 사용자가 확인하거나 정정할 실행 여건이 있다. 승인 계획·전체 도구 목록의 사전 입력은 필요하지 않다.

### 후행 조건

- 성공: 확인한 여건과 아직 모르는 부분이 구분되며 이후 제안에 반영된다.
- 취소·실패: 기존 확인값을 유지한다. 기본 도구 가정을 실제 보유 확인으로, 빈 시간을 가용 시간으로 확정하지 않는다.

### 이벤트 흐름

트리거: 사용자가 실행 여건을 설정·수정하거나 시스템의 짧은 확인 요청에 응답한다.

기본 흐름:

1. 시스템이 수정 가능한 일반적인 한국 가정의 조리도구 기본 목록과 알려진 시간 여건을 제시한다.
2. 사용자가 없는 도구를 제외하고 실제 사용할 수 있는 시간 등을 필요한 범위에서 확인한다.
3. 시스템이 확인한 조건과 미상 조건을 구분해 저장한다.
4. 이후 변경 후보·안내에서 해당 조건을 사용한다.

대안·예외:

- 2단계에서 식재료를 확인하더라도 도구와 별개로 다룬다. 수량·유통기한 관리까지 포함하는 것은 미정이다.
- 사용자가 추정 가용 시간을 사용할 수 없다고 정정하면 이후 후보에서 확인된 가용 시간으로 쓰지 않는다.
- 저장 취소·실패 시 기존 값을 유지하며, 여건 변경이 승인 계획에 미치는 영향은 UC-PLAN-002에서 검토한다.

### 비기능 요구사항

- NFR-USABILITY-001: 전체 목록 직접 입력 대신 기본값 제외 과제의 조작 수·시간을 측정한다.
- NFR-DATA-001: 확인·정정한 도구·시간 조건의 재실행 후 조회를 확인한다.
- NFR-PRIVACY-001: 생활 시간 등 개인 조건의 보관·전송 범위를 확인한다.

## UC-LINK-001: 데이터 출처 연결과 수집 상태 확인하기

### 개요

수집할 출처와 권한을 선택하고 마지막 수집·실패·재연결 상태를 확인한다. 연결 요구: REQ-INGEST-003. 지속 수집은 사용자 방향이며 권한·재시도 상세는 개발 제안이다. 실제 지원 경로는 Q-11/Q-12의 기기 시험 전이다.

### 관련 액터

- 주 액터: 사용자.
- 보조 액터: Android 권한 시스템, 지원 결제·건강 자료 제공 시스템.

### 우선순위

P1(높음·제안). 수집 가능 범위와 누락을 정확히 이해하기 위한 전제다.

### 선행 조건

- 연결 설정·상태 확인 기능에 접근할 수 있다. 권한 부여·외부 자료 도착은 선행 조건으로 요구하지 않는다.

### 후행 조건

- 성공: 실제 권한·연결 상태와 마지막 수집·실패를 구분하여 확인한다. 허용 범위에서만 수집을 수행한다.
- 거부·회수·실패: 해당 범위의 수집이 불가하거나 중단됐음을 표시한다. 기존 기록은 그대로 두며 권한 부여를 수집 완료로 표시하지 않는다.

### 이벤트 흐름

트리거: 사용자가 출처 연결·권한 변경·상태 조회·재연결을 요청한다.

기본 흐름:

1. 시스템이 지원 후보 출처, 필요한 접근 범위와 현재 상태를 제시한다.
2. 사용자가 출처를 선택하고 Android 등 해당 시스템에서 필요한 권한을 결정한다.
3. 시스템이 실제 권한·기능 지원 상태를 확인한다.
4. 허용된 경로의 수집을 시작하거나 이어가고, 실제 수집 결과와 상태를 표시한다.

대안·예외:

- 조회만 요청하면 2단계 권한 요청 없이 현재 상태를 보여준다.
- 2~3단계의 거부·미지원·권한 회수는 해당 범위의 수집 불가로 표시한다. 자동 재요청·재시도 주기는 미정이다.
- 4단계의 연결 성공 후 자료가 아직 없으면 수집 대기·지연과 실제 0을 구분한다. 재연결 시 허용된 보완 범위와 중복 규칙을 적용한다.

### 비기능 요구사항

- NFR-PRIVACY-001: 출처별 접근·전송·보관 범위가 안내와 일치하는지 확인한다.
- NFR-USABILITY-001: 서로 다른 권한과 상태를 사용자가 식별할 수 있는지 대표 과제로 확인한다.
- NFR-CAPTURE-001: 재연결·지속 수집의 지연·배터리 부담을 실기로 측정한다. 목표치는 미정이다.

## UC-EXPENSE-001: 결제 자료를 자동으로 가져오기

### 개요

허용한 출처의 지원 결제 자료를 가져와 반복 입력을 줄인다. 연결 요구: REQ-INGEST-001, REQ-INGEST-003, REQ-INGEST-004. 수집 목적은 사용자 방향, 중복·정정 상세는 개발 제안이다. 알림 추출은 검증 후보이며 Q-11/Q-14에서 지원 필드·분류·집계 경계를 결정한다.

### 관련 액터

- 시작 액터: 지원 결제 자료 제공 시스템. 초기 후보는 삼성페이·카드사 앱의 결제 알림 경로다.
- 수혜 액터: 사용자. 보조 액터: 경로에 필요한 Android 권한·알림 시스템.

### 우선순위

P1(높음·제안). 지출을 일일이 입력하는 부담을 줄이는 핵심 경로다.

### 선행 조건

- 대상 출처와 수집 범위가 허용되어 있고 지원 자료를 읽을 수 있다. 최초 관찰 완료·승인 계획은 필요하지 않다.

### 후행 조건

- 성공: 가져온 필드·출처·사건 시각·확인 상태가 보존되고 반복 수신으로 지출 집계가 증가하지 않는다.
- 부분·실패: 읽지 못한 값·불명확한 중복·분류를 미상·후보 상태와 구분한다. 저장 실패를 완료로 표시하지 않고 결제를 실제 섭취 사실로 만들지 않는다.

### 이벤트 흐름

트리거: 지원 자료가 도착·변경되거나 허용된 가져오기 작업이 실행된다.

기본 흐름:

1. 시스템이 현재 출처·권한을 확인하고 읽을 수 있는 결제 필드를 추출한다.
2. 기존 기록과 같은 사건인지, 정정·취소인지 확인한다.
3. 알려진 값과 출처·상태를 저장하고 중복 확정 집계를 방지한다.
4. 필요한 분류·음식 등 확인 항목만 UC-INTERACT-001/002로 연결한다. 저장한 자료는 관찰·분석에서 사용할 수 있게 한다.

대안·예외:

- 1단계에서 권한이 회수되면 해당 수집을 중단하고 UC-LINK-001의 상태에 반영한다. 미지원 형식·가려진 값은 만들어내지 않는다.
- 2단계에서 같은 원본이 재도착하면 같은 사건으로 처리한다. 출처 간 동일성이 불명확하면 두 건의 실제 식비로 확정하지 않는다.
- 취소·환불은 신규 식사로 해석하지 않는다. 원거래 연결·기간별 환불 집계 상세는 미정이다.
- 3단계 저장에 실패하면 수집 완료로 표시하지 않는다. 가져올 수 없는 과거 전체 내역의 복원을 보장하지 않는다.

### 비기능 요구사항

- NFR-DATA-001: 성공 저장한 필드·출처·처리 상태를 정상 재실행 후 조회한다.
- NFR-PRIVACY-001: 결제 원문 전체의 외부 AI 전송을 가정하지 않고 실제 전송·보관 범위를 확인한다.
- NFR-CAPTURE-001: 수집 지연·반복 처리·배터리 부담을 측정한다. 즉시 감지를 합격 기준으로 확정하지 않는다.

## UC-ACTIVITY-001: 활동 자료를 자동으로 가져오기

### 개요

허용한 건강 경로에서 지원되는 걸음·운동 자료를 지속 수집한다. 연결 요구: REQ-INGEST-002, REQ-INGEST-003, REQ-INGEST-004. 사용자 방향이며 출처·중복 처리 상세는 개발 제안이다. Health Connect는 우선 검증 후보이고 실제 필드·백그라운드 지원은 Q-12에서 확인한다.

### 관련 액터

- 수혜 액터: 사용자. 보조 액터: Android 권한 시스템.

### 우선순위

P1(높음·제안). 활동 재입력 없이 지속 관찰하기 위한 핵심 경로다.

### 선행 조건

- 지연·부분·실패: 미수집 범위를 실제 비활동과 구분한다. 기존 성공 기록을 유지하고 수집 실패를 완료로 표시하지 않는다.

### 이벤트 흐름

트리거: 자료 도착·변경 또는 허용된 동기화 작업 실행.

기본 흐름:

1. 시스템이 지원 기능과 현재 허용된 자료 범위를 확인한다.
2. 제공된 걸음·운동 자료와 출처·시각·원본 식별 정보를 읽는다.
3. 재수집·여러 출처·정정 여부를 확인하고 수집 자료와 처리 상태를 저장한다.
4. 관찰·실행 기록과 기간 분석에 사용하고 자동으로 알 수 없는 체감 등만 필요한 경우 짧게 확인한다.

대안·예외:

- 1단계 권한 회수·미지원은 UC-LINK-001에 표시한다. 허용되지 않은 범위는 읽지 않는다.
- 2단계 자료가 늦게 도착하면 원래 활동 시각과 가져온 시각을 구분한다. 운동 직후 수신을 보장하지 않는다.
- 3단계 여러 출처의 걸음을 무조건 합산하지 않는다. 동일성·집계·출처 우선순위 상세는 기기 시험·설계에서 결정한다.
- 자료 수정·삭제는 출처의 변경 정보와 기존 처리 상태를 구분하여 반영하는 초안이며 상세 동기화 계약은 미정이다. 저장 실패는 완료로 표시하지 않는다.

### 비기능 요구사항

- NFR-DATA-001: 성공 수집 자료·출처·시각이 정상 재실행 후 유지되는지 확인한다.
- NFR-PRIVACY-001: 허용 건강 자료의 보관·외부 전송 범위를 확인한다.
- NFR-CAPTURE-001: 지연·백그라운드 동작·배터리 부담을 실기에서 측정한다. 정확히 가져온 값의 반복 수동 입력 부담도 확인한다.

## UC-INTERACT-001: 필요한 시점에 기록·실행·조정 안내받기

### 개요

사용자가 먼저 앱을 찾지 않아도 필요한 기록 보완·행동·계획 변경을 안내받는다. 연결 요구: REQ-INTERACT-001. 사용자 방향이며 빈도·조용한 시간·묶음·미루기는 Q-05, 노출은 Q-13에서 결정한다.

### 관련 액터

- 수신 액터: 사용자. 보조 액터: Android 알림 시스템.
- 자료 도착·합의한 시점 도래가 시작 계기다. 앱 내부 스케줄러를 외부 액터로 만들지 않는다.

### 우선순위

P1(높음·제안). 자발적인 앱 실행에만 의존하지 않는 상호작용의 출발점이다.

### 선행 조건

- 안내할 유효한 확인 항목·실행 항목·변경 후보가 있다. 시각 기반 안내는 사용자와 합의한 시점을 전제로 한다.
- 알림 권한은 표시 가능 여부를 결정한다. 차단 상태에서도 미처리 항목 자체는 구분한다.

### 후행 조건

- 성공: 안내가 해당 항목의 지원되는 응답·조회 경로로 연결된다. 알림 전달과 사용자 응답 완료는 구분된다.
- 차단·미응답·실패: 미처리 항목과 기존 기록·승인 계획을 보존한다. 사용자가 응답했다고 대신 기록하지 않는다.

### 이벤트 흐름

트리거: 지원 사건 도착 또는 사용자와 합의한 보완·실행·검토 시점 도래.

기본 흐름:

1. 시스템이 안내 대상의 현재 상태와 이미 처리됐는지 확인한다.
2. 알림 권한·노출 정책과 합의한 빈도 정책을 확인한다.
3. 필요한 내용과 고정 선택·짧은 입력 또는 관련 항목 진입점을 구성하여 알림 시스템에 전달한다.
4. 사용자가 안내를 확인하면 UC-INTERACT-002 또는 해당 조회·실행·변경 검토로 연결한다.

대안·예외:

- 1단계 대상이 이미 처리됐으면 같은 질문을 반복 생성하지 않는다. 오래된 안내 응답은 현재 상태를 다시 확인한다.
- 2단계 권한 차단·잠금 노출 제한이 있으면 지원 범위만 표시하고 미처리 항목을 유지한다. 대체 진입점의 상세는 미정이다.
- 3~4단계 전달 지연·미응답·알림 해제는 실행 완료나 계획 변경 승인으로 간주하지 않는다. 재안내·미루기 주기는 미정이다.

### 비기능 요구사항

- NFR-LOCK-001: 잠금 상태와 노출 설정에 따른 실제 표시 내용을 확인한다.
- NFR-CAPTURE-001: 안내 빈도·지연·배터리 부담을 측정한다. 사건 발생 시각과 수집·알림 시각을 구분한다.
- NFR-USABILITY-001: 안내에서 해당 항목으로 가는 조작 수·시간을 측정한다.

<a id="uc-interact-002"></a>

## UC-INTERACT-002: 알림·짧은 UI에서 빠르게 확인하기

### 개요

미리 확보한 값은 활용하고 자동으로 알 수 없는 내용만 고정 선택·단문으로 보완한다. 연결 요구: REQ-INTERACT-002, REQ-ROUTINE-001, REQ-RECORD-001. 사용자 방향이며 필수 확인·버튼·자동 분류는 Q-09/Q-14, 잠금 상태는 Q-13에서 결정한다.

### 관련 액터

- 주 액터: 사용자. 보조 액터: Android 알림·인증 시스템.

### 우선순위

P1(높음·제안). 자동 수집만으로 채울 수 없는 정보의 입력 부담을 줄인다.

### 선행 조건

- 응답을 연결할 기록·확인 항목이 보존되어 있다. 승인 계획은 필수 전제가 아니다.
- 알림 동작 또는 해당 항목이 미리 채워진 짧은 입력 화면에 접근할 수 있다.

### 후행 조건

- 성공: 응답이 올바른 대상에 저장되고 확인 상태·남은 미상 정보를 구분하며 저장 결과를 알 수 있다.
- 취소·실패·미응답: 기존 성공 기록과 미확인 상태를 유지한다. 중복 응답이 새 기록·중복 지출로 증가하지 않는다.

### 이벤트 흐름

트리거: 사용자가 알림 동작·답장 또는 연결된 짧은 화면에서 응답한다.

기본 흐름:

1. 시스템이 이미 아는 값과 보완할 항목을 제시한다.
2. 사용자가 고정 선택·짧은 내용으로 응답한다.
3. 시스템이 대상의 현재 상태·응답 유효성을 확인하고 해당 기록에 저장한다.
4. 저장 결과와 필요한 경우 남은 확인 내용을 보여준다.

대안·예외:

- 잠금 상태에서 처리가 제한되면 OS·노출 정책에 따라 인증 또는 해당 항목의 짧은 화면으로 연결한다. 항상 인증 없이 처리한다고 보장하지 않는다.
- 2단계 무응답·알림 해제는 확인 완료가 아니다. 미루기·재안내 상세는 미정이다.
- 3단계 반복 응답·이미 정정된 대상·오래된 알림은 현재 상태를 확인하여 중복 저장·잘못된 반영을 막는다(D0.1 초안).
- 3단계 저장 실패 시 성공으로 표시하지 않는다. 결제 분류만 응답했으면 음식·섭취량·식사 사실을 추가로 만들어내지 않는다.

### 비기능 요구사항

- NFR-USABILITY-001: 분류·실행 여부 등 대표 과제의 필수 입력·조작 수·시간을 측정한다.
- NFR-DATA-001: 성공 응답이 정상 재실행 후 남는지 확인한다.
- NFR-LOCK-001: 잠금·인증·노출 설정별 응답 경로와 정보 표시를 확인한다.
- NFR-CAPTURE-001: 빠른 응답의 실제 지연과 반복 동작 부담을 측정한다.

## UC-RECORD-001: 실제 생활 기록을 조회·보완·정정하기

### 개요

식사·활동·지출의 실제 기록을 계획과 구분해 조회하고 누락·오류를 보완한다. 연결 요구: REQ-ROUTINE-001, REQ-RECORD-001, REQ-INGEST-004. 사용자 방향이며 필드·부분 입력·출처 정정 방식은 상세 초안이다(Q-09/Q-14).

### 관련 액터

- 주 액터: 사용자. 외부 수집 기록의 정정에서는 원래 출처와 사용자 보완의 관계를 다룬다. 외부 원장 자체를 수정하는 사례는 아니다.

### 우선순위

P1(높음·제안). 자동 수집이 불완전한 상황에서도 실제 생활을 기록할 수 있어야 한다.

### 선행 조건

- 기록 조회·입력에 접근할 수 있다. 최초 기록이나 빈 기간도 대상이며 계획·연동 권한·기존 기록은 필수 전제가 아니다.

### 후행 조건

- 성공: 조회한 실제 기록 또는 성공 저장한 보완·정정을 확인할 수 있다. 모르는 값은 미상으로 남고 계획과 구분된다.
- 조회·취소·실패: 기존 성공 기록·승인 계획을 유지한다. 조회 자체나 분석 수정으로 실제 기록을 다시 쓰지 않는다.

### 이벤트 흐름

트리거: 사용자가 기록 확인·누락 추가·오류 정정을 요청한다.

기본 흐름:

1. 시스템이 대상 날짜·사건의 실제 기록과 출처·확인 상태를 보여준다.
2. 사용자가 필요한 경우 아는 정보만 추가하거나 정정한다.
3. 시스템이 대상·중복·수정 내용을 확인하여 실제 기록으로 저장한다.
4. 저장 결과를 보여주고 수정 자료를 후속 분석에서 구분하여 사용할 수 있게 한다.

대안·예외:

- 조회만 하면 2~4단계의 수정 저장 없이 종료한다. 빈 기간은 기록 없음과 실제 0을 구분한다.
- 수동 보완과 자동 수집이 같은 사건을 가리키면 중복 처리 규칙을 적용한다. 동일성 판단이 부족하면 불확실 상태로 둔다.
- 원본 결제·활동의 취소·정정과 사용자 해석 보완을 구분한다. 상세 이력·환불 규칙은 미정이다.
- 저장 실패·입력 취소 시 완료로 표시하지 않는다. 수정 기록에 영향받는 분석·제안의 재검토 표시 방식은 개발 제안이다.

### 비기능 요구사항

- NFR-DATA-001: 성공 저장한 실제 기록과 수정 결과가 정상 재실행 후 조회되는지 확인한다.
- NFR-USABILITY-001: 미리 채우기·부분 입력으로 대표 보완 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 지정 자료량에서 날짜별 조회·수정 저장 시간을 따로 측정한다. 목표치는 미정이다.
- NFR-PRIVACY-001: 실제 생활·지출 자료의 보관·전송·삭제 방식을 확인한다.

## UC-ANALYSIS-001: 기간별 생활패턴과 분석 근거 확인하기

### 개요

3·7·15일 단위의 식사·가용 시간·지출·활동 패턴과 근거·정보 부족을 확인한다. 연결 요구: REQ-ROUTINE-002, REQ-ROUTINE-004. 사용자 방향이며 창 계산·달력일/기록일·분석 개시·자료 충족 조건은 Q-08에서 결정한다.

### 관련 액터

- 주 액터: 사용자. 분석 시점 도래로 먼저 요약할 수도 있다.
- 외부 AI를 채택하면 보조 액터로 참여한다. 외부 AI 이용은 현재 확정하지 않았다.

### 우선순위

P1(높음·제안). 새 식사·운동 계획을 먼저 강요하지 않고 관찰 근거로 개선하는 핵심 단계다.

### 선행 조건

- 대상 기간의 기록 유무·수집 범위를 조회할 수 있다. 기록이 충분하다는 조건을 조회 자체의 전제로 두지 않는다.

### 후행 조건

- 성공: 대상 기간·실제 기록 범위·확인된 경향·근거·미상 정보를 구분하여 확인한다.
- 부족·실패: 분석할 수 있는 범위와 부족·실패를 구분한다. 미수집을 0·결식·비활동으로, 기록만으로 신체 변화가 발생했다고 판정하지 않는다.

### 이벤트 흐름

트리거: 사용자가 기간 분석을 조회하거나 합의할 분석 시점이 도래한다.

기본 흐름:

1. 시스템이 3·7·15일 중 대상 단위에 해당하는 기간과 수집 범위를 확인한다.
2. 기록된 식사·시간 여건·지출·활동을 요약하고 경향과 근거를 연결한다.
3. 분석 대상 기간·자료 범위·불확실한 부분을 함께 제시한다.
4. 사용자가 결과를 확인하고 필요하면 UC-ANALYSIS-002 또는 UC-CHANGE-001로 이어간다.

대안·예외:

- 1~2단계 기록 없음·자료 부족이면 분석 가능한 범위와 부족한 정보를 표시한다. 관찰 연장·추가 확인·제한적 제안의 선택 정책은 미정이다.
- 기간만 지났다는 이유로 통계적으로 확정된 패턴이라고 표현하지 않는다. 활동 자료의 지연 도착·정정에 따른 재분석 방식도 미정이다.
- 분석·외부 서비스 실패 시 실패를 표시하고 실제 기록·승인 계획을 유지한다. 기존 요약을 보인다면 현재 자료와의 시점 차이를 구분하는 방향이다.

### 비기능 요구사항

- NFR-PERFORMANCE-001: 기간·자료량·연결 조건별 요약 조회와 분석 생성 시간을 구분해 측정한다.
- NFR-USABILITY-001: 사용자가 근거·미상·대상 기간을 식별하는 과제의 조작 수·시간을 측정한다.
- NFR-PRIVACY-001: 분석에 사용하는 필드와 외부 AI 채택 시 전송·보관 범위를 확인한다.

## UC-ANALYSIS-002: 분석 해석과 가용 시간 정정하기

### 개요

실제 기록에 대한 잘못된 해석이나 추정 가용 시간을 정정하여 다음 추천에 반영한다. 연결 요구: REQ-ROUTINE-003. 기존 개발 제안이며 확인·정정 UI와 재분석 방식은 미정이다.

### 관련 액터

- 주 액터: 사용자. 재분석에서 외부 AI를 채택하면 보조 액터로 참여한다.

### 우선순위

P2(보통·제안). 분석의 잘못된 가정을 바로잡는 보완 흐름이다.

### 선행 조건

- 확인·정정할 분석 해석 또는 추정 가용 시간이 제시되어 있다.

### 후행 조건

- 성공: 사용자가 확인한 조건을 다음 제안에 반영한다. 사용할 수 없다고 정정한 시간은 확인된 가용 시간으로 쓰지 않는다.
- 취소·실패: 기존 성공 저장 상태를 유지하고 정정 완료로 표시하지 않는다. 해석 정정만으로 원본 생활 기록·승인 계획을 바꾸지 않는다.

### 이벤트 흐름

트리거: 사용자가 분석 해석·가용 시간의 오류를 발견하여 정정을 요청한다.

기본 흐름:

1. 시스템이 대상 해석·근거·추정 조건을 보여준다.
2. 사용자가 실제로 사용할 수 없는 시간 등 잘못된 내용을 정정한다.
3. 시스템이 해석·조건의 정정으로 저장한다.
4. 정정 결과를 확인시키고 이후 분석·변경 후보에 사용할 조건으로 반영한다.

대안·예외:

- 2단계 문제의 원인이 실제 기록 오류라면 UC-RECORD-001의 정정으로 연결한다.
- 수정 취소·저장 실패는 성공으로 표시하지 않는다. 기록 정정과 해석 정정을 섞지 않는다.
- 이미 생성한 제안의 재검토 표시·재생성 시점은 개발 제안이며 미정이다. 승인 계획 변경은 UC-PLAN-002를 따른다.

### 비기능 요구사항

- NFR-USABILITY-001: 단순 정정 과제의 필수 입력·조작 수·시간을 측정한다.
- NFR-DATA-001: 성공 저장한 확인 조건·정정 결과가 정상 재실행 후 조회되는지 확인한다.
- NFR-PRIVACY-001: 생활 시간 등 정정 정보가 외부 분석에 전달되는 범위를 확인한다.

## UC-CHANGE-001: 관찰에 근거한 변경 후보 검토·선택하기

### 개요

관찰한 루틴과 관리 방향을 연결하여 실행 가능한 변화 후보를 비교·선택한다. 연결 요구: REQ-CHANGE-001. 사용자 방향이며 제안 개수·기간·부담과 목표 상충 우선순위는 Q-10 등에서 결정한다.

### 관련 액터

- 주 액터: 사용자. 외부 AI를 채택하면 제안 생성의 보조 액터로 참여한다.

### 우선순위

P1(높음·제안). 기존 생활의 어떤 부분을 왜 바꿀지 선택하는 핵심 단계다.

### 선행 조건

- 관찰 기록·분석 범위, 선택한 방향과 알려진 실행 여건을 참조할 수 있다. 최초 제안 전에 확인할 정보 충족 조건은 Q-08/Q-09에서 결정한다.

### 후행 조건

- 성공: 현재 패턴·바꿀 행동·이유·필요 시간·예상 비용을 확인하고 시도할 변경을 선택한다.
- 미선택·부적합·실패: 기존 승인 계획·실제 기록을 유지한다. 선택하지 않은 후보나 실행 여건을 충족하지 못한 후보를 승인 계획으로 적용하지 않는다.

### 이벤트 흐름

트리거: 사용자가 분석 후 변경 후보를 요청하거나 제시된 후보를 검토한다.

기본 흐름:

1. 시스템이 관찰 근거·현재 방향·확인한 시간·도구 등 조건을 확인한다.
2. 조건에 맞는 행동 변경 후보와 이유·필요 시간·예상 비용을 제시한다. 추정·미상 값은 구분한다.
3. 사용자가 후보를 비교하고 시도할 변경을 선택한다.
4. 선택한 변경을 UC-PLAN-001의 계획 검토에 사용할 입력으로 연결한다.

대안·예외:

- 1단계 정보가 부족하면 부족한 부분을 보여준다. 관찰 연장·추가 질문·제한적 제안의 정책은 미정이다.
- 2단계 확인된 사용 불가 시간·없는 도구와 충돌하면 실행 가능한 후보로 제시하지 않는다. 적합한 후보가 없으면 찾았다고 표시하지 않는다.
- 제안 실패·미선택 시 현재 상태를 유지한다. 후보 선택과 최종 계획 승인은 구분한다.

### 비기능 요구사항

- NFR-USABILITY-001: 이유·시간·비용을 비교하고 변경을 선택하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 자료·조건별 후보 생성·조회 시간을 측정한다. 응답 목표치는 미정이다.
- NFR-PRIVACY-001: 추천에 쓰는 생활·지출 자료와 외부 전송 범위를 확인한다.

<a id="uc-plan-001"></a>

## UC-PLAN-001: 기간별 계획 검토 및 승인

### 개요

관찰·분석·선택한 변경을 반영한 기간 계획 초안을 검토·수정하고 실행 기준으로 승인한다. 기존 ID와 목적을 유지한다. 연결 요구: REQ-PLAN-001, REQ-PLAN-003. 사용자 방향이며 월·주 역할·승인 묶음·출력 범위는 Q-01, 필수 입력·가정은 Q-08/Q-09에서 결정한다.

### 관련 액터

- 주 액터: 사용자. 외부 AI를 채택하면 초안 생성의 보조 액터로 참여한다.

### 우선순위

P1(높음·제안). AI 제안과 사용자가 채택한 실행 계획을 구분하는 핵심 경계다.

### 선행 조건

- 최초 사용에서는 기존 루틴 관찰·분석과 변경 검토를 먼저 거친다. 최초 관찰의 완료·정보 충족 조건은 미정이다.
- 계획할 기간과 알려진 목표·예산·실행 여건을 참조할 수 있다. 기존 승인 계획이 없는 첫 계획도 허용한다.

### 후행 조건

- 성공: 사용자가 검토한 초안의 승인·저장이 성공하고 해당 계획이 실행 안내의 기준이 된다.
- 초안 검토·거절·취소·생성/저장 실패: 기존 승인 계획이 있으면 유지하고 실제 기록을 보존한다. 기존 승인 계획이 없으면 초안을 승인 계획으로 표시하지 않는다.

### 이벤트 흐름

트리거: 사용자가 관찰·변경 검토 후 기간 계획을 요청한다.

기본 흐름:

1. 사용자가 계획할 기간을 선택·요청한다.
2. 시스템이 루틴 분석·방향·선택한 변경·알려진 조건으로 계획 초안과 예상 지출·주요 가정을 제시한다.
3. 사용자가 내용을 검토하고 필요하면 수정을 요청한다. 시스템이 수정 초안을 제시한다.
4. 사용자가 검토한 초안을 명시적으로 승인한다.
5. 시스템이 승인 결과를 저장하고 성공한 계획을 실행 안내의 기준으로 표시한다.

대안·예외:

- 2단계 정보 부족은 확인할 부분과 사용한 가정을 표시한다. 모든 항목을 필수로 입력받거나 장보기 전용 기능까지 확정한 것은 아니다.
- 생성 실패 시 실패를 알리고 기존 계획을 유지한다. 재시도·수동 작성의 상세 지원은 미정이다.
- 3~4단계 검토·수정·취소 중에는 기존 승인 계획을 바꾸지 않는다.
- 5단계 저장 실패는 승인 완료로 표시하지 않는다. 오래된 초안·기준 버전 불일치 시 현재 상태를 확인하고 재검토하는 방향은 D0.1의 초안이다.

### 비기능 요구사항

- NFR-DATA-001: 승인·저장 성공 후 정상 재실행해 실행 기준이 유지되는지 확인한다.
- NFR-USABILITY-001: 기간 계획의 가정·내용·승인 대상을 확인하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 초안 생성·수정 생성·승인 저장 시간을 각각 측정한다. 목표 수치는 미정이다.
- NFR-PRIVACY-001: 초안 생성에 필요한 데이터의 전송·보관 범위를 확인한다.

## UC-PLAN-002: 상황 변화·일일 피드백으로 승인 계획 조정하기

### 개요

매일의 자료·응답·상황 변화에 따라 변경 초안을 검토하고 승인한 범위를 반영한다. 연결 요구: REQ-PLAN-002, REQ-PLAN-004. 사용자 방향이며 사전 위임·작은 변경·빠른 승인 범위는 Q-06에서 결정한다. 현재 초안은 미승인 자동 적용을 전제하지 않는다.

### 관련 액터

- 주 액터: 사용자. 외부 AI 채택 시 변경 생성의 보조 액터, 알림을 통한 검토 시 Android 알림 시스템이 참여한다.

### 우선순위

P1(높음·제안). 지속 수집을 실제 계획 개선에 연결하면서 승인 경계를 지킨다.

### 선행 조건

- 변경 기준이 되는 승인 계획이 있다. 변경에 필요한 새 자료·사용자 응답 또는 변경 요청을 참조할 수 있다.

### 후행 조건

- 성공: 사용자가 검토·승인한 변경의 저장이 성공하고 새 승인 기준이 표시된다. 기존 실제 식사·운동·결제 기록은 바뀌지 않는다.
- 거절·무응답·취소·실패: 기존 승인 계획과 실제 기록을 유지한다. 변경 초안 생성만으로 실행 기준을 전환하지 않는다.

### 이벤트 흐름

트리거: 사용자가 변경을 요청하거나 새 자료·일일 응답에 따라 변경 검토가 필요해진다.

기본 흐름:

1. 시스템이 현재 승인 계획·관련 실제 기록·변경 사유를 확인한다.
2. 변경 초안과 이유·범위·차이·알려진 예상 지출 등 영향을 제시한다.
3. 사용자가 필요한 수정을 요청하거나 적용할 변경을 승인한다.
4. 시스템이 현재 기준·검토한 초안을 확인하여 승인 결과를 저장하고 실행 안내를 갱신한다.

대안·예외:

- 승인 계획이 없으면 기존 계획 수정으로 처리하지 않고 UC-PLAN-001의 최초 검토 흐름으로 안내한다.
- 매일 새 자료가 들어와도 변경할 필요가 없으면 변경이 있다고 만들어내지 않는다. 알림·생성 빈도 정책은 미정이다.
- 2~3단계 생성 실패·거절·무응답·취소는 기존 기준을 유지한다. 빠른 승인 UI는 UC-INTERACT-002로 연결할 수 있다.
- 4단계 저장 실패·기준 버전 불일치·오래된 알림 응답 시 현재 상태를 확인하고 잘못된 버전 전환·중복 반영을 막는다(D0.1 초안).

### 비기능 요구사항

- NFR-DATA-001: 새 승인 기준과 기존 실제 기록이 정상 재실행 후 보존되는지 확인한다.
- NFR-USABILITY-001: 변경 이유·차이·영향을 확인하고 승인/거절하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 변경 생성과 승인 저장의 응답 시간을 구분해 측정한다.
- NFR-LOCK-001: 알림에서 검토·승인할 경우 잠금 상태의 노출·인증 범위를 확인한다.

## UC-MEAL-001: 계획한 요리의 실행 안내받기

### 개요

계획한 요리에 필요한 재료·조리 방법을 확인하여 실제 준비·조리로 옮길 수 있게 한다. 연결 요구: REQ-MEAL-001. 사용자 방향이며 안내의 상세 수준·재료 정보 범위는 미정이다. 상세 재고 관리 기능을 전제하지 않는다.

### 관련 액터

- 주 액터: 사용자. 외부 AI로 안내를 생성하도록 선택하면 보조 액터로 참여한다.

### 우선순위

P2(보통·제안). 관찰·승인 흐름 이후 실제 행동을 지원하는 상세 기능이다.

### 선행 조건

- 안내 대상 요리와 알려진 조리 여건이 있다. 초안을 미리 볼 경우에도 승인 여부를 구분하며 승인 전 실행을 요구하지 않는다.

### 후행 조건

- 성공: 대상 요리의 필요한 재료·조리 방법과 알려진 실행 조건을 확인한다.
- 안내 불가·실패: 정보 부족·실패를 표시한다. 안내 조회만으로 식사 완료·실제 지출을 기록하거나 승인 계획을 바꾸지 않는다.

### 이벤트 흐름

트리거: 사용자가 대상 요리의 안내를 열거나 해당 식사 실행 안내에서 진입한다.

기본 흐름:

1. 시스템이 대상 요리와 관련 계획 상태·확인된 조리 여건을 확인한다.
2. 필요한 재료·조리 단계 등 실행 정보를 제시한다.
3. 사용자가 내용을 확인한다. 실제 식사 뒤의 기록은 UC-ACTION-001 또는 UC-RECORD-001로 연결한다.

대안·예외:

- 없는 도구·사용 불가 시간이 확인되면 해당 조건을 충족하는 것으로 안내하지 않는다. 요리가 어려우면 UC-MEAL-002의 대안을 검토한다.
- 재료 보유 여부·비용·시간을 알 수 없으면 미상·추정으로 구분한다. 재료가 있다고 임의로 확정하지 않는다.
- 안내 생성·조회 실패 시 실패를 표시하고 기존 계획·기록을 유지한다.

### 비기능 요구사항

- NFR-USABILITY-001: 재료·조리 순서를 찾아 실행에 필요한 내용을 확인하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 저장된 안내 조회와 새 안내 생성의 응답 시간을 따로 측정한다.
- NFR-PRIVACY-001: 외부 안내 생성 시 필요한 개인 조건의 전송 범위를 확인한다.

## UC-MEAL-002: 요리하기 어려울 때 식사 대안 찾기

### 개요

현재 시간·예산·알려진 제약에 맞는 외식 등 식사 대안을 검토한다. 연결 요구: REQ-MEAL-002, REQ-CHANGE-001. 사용자 방향이며 후보의 상세 정보·제약·가격 정보 수준은 초안이다. 실시간 매장 가격 조회·주문·결제는 확정 범위가 아니다.

### 관련 액터

- 주 액터: 사용자. 외부 AI 채택 시 후보 생성의 보조 액터가 참여한다. 음식점·배달 서비스 직접 연동은 필수 액터로 두지 않는다.

### 우선순위

P2(보통·제안). 요리 계획을 수행하기 어려운 상황의 실행 대안을 구체화한다.

### 선행 조건

- 식사 대안 요청과 알려진 시간·예산·제약을 참조할 수 있다. 기존 요리 계획이 없는 대안 요청도 가능하다.

### 후행 조건

- 성공: 알려진 여건에 맞는 후보와 선택에 필요한 추정·미상 정보를 확인한다.
- 미선택·실패: 기존 승인 계획·실제 기록을 유지한다. 대안 조회·선택만으로 실제 식사·지출이 발생했다고 기록하지 않는다.

### 이벤트 흐름

트리거: 사용자가 요리할 수 없거나 다른 식사 대안을 원한다고 요청한다.

기본 흐름:

1. 시스템이 현재 여건·알려진 제약과 관련 계획이 있는지 확인한다.
2. 가능한 식사 대안과 알려진 시간·예상 비용·선택 이유를 제시한다.
3. 사용자가 대안을 검토한다.
4. 승인 계획을 바꿀 필요가 있으면 UC-PLAN-002로, 실제로 먹은 뒤의 기록은 UC-ACTION-001 또는 UC-RECORD-001로 연결한다.

대안·예외:

- 1~2단계 정보가 부족하면 가정·미상 정보를 표시한다. 실시간 가격·영업 여부를 확인했다고 가정하지 않는다.
- 알려진 제약을 만족하는 후보가 없으면 적합한 대안이 있다고 표시하지 않는다.
- 후보 생성 실패·거절·무응답은 기존 계획을 유지한다. 승인 계획이 없으면 변경 승인을 거친 것으로 표시하지 않는다.

### 비기능 요구사항

- NFR-USABILITY-001: 후보·비용·제약을 비교하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 후보 생성·조회 시간을 자료·연결 조건별로 측정한다.
- NFR-PRIVACY-001: 추천에 필요한 개인 조건의 외부 전송·보관 범위를 확인한다.

## UC-EXERCISE-001: 선택한 방향·시간에 맞는 운동 안내받기

### 개요

사용자가 선택한 운동 지침과 확인된 가용 시간에 맞는 수행 안내를 확인한다. 연결 요구: REQ-EXERCISE-001. 사용자 방향이며 운동 종류·강도·안내 수준·필수 제약은 Q-04/Q-10에서 결정한다. 정밀 신체 측정이나 의료적 처방은 현재 범위가 아니다.

### 관련 액터

- 주 액터: 사용자. 외부 AI 채택 시 안내 생성의 보조 액터가 참여한다. 워치의 활동 수집은 UC-ACTIVITY-001에서 다룬다.

### 우선순위

P2(보통·제안). 관찰과 계획 검토 이후 운동 실행의 상세 지원을 구체화한다.

### 선행 조건

- 선택한 운동 방향과 알려진 시간·실행 여건을 참조할 수 있다. 필수 조건의 범위는 Q-04에서 정하며 운동 기록 자동 수집 권한을 안내 조회의 필수 전제로 두지 않는다.

### 후행 조건

- 성공: 선택한 방향·알려진 시간 여건에 맞는 운동 수행 안내를 확인한다.
- 부족·실패: 정보 부족·미지원 안내 범위·실패를 구분한다. 안내 조회만으로 운동 완료나 근육량 변화가 측정됐다고 기록하지 않는다.

### 이벤트 흐름

트리거: 사용자가 운동 안내를 요청하거나 관련 실행 안내를 확인한다.

기본 흐름:

1. 시스템이 선택한 지침·관련 계획 상태·확인한 가용 시간을 확인한다.
2. 합의할 안내 수준 안에서 실행 정보를 제시한다.
3. 사용자가 안내를 확인한다.
4. 실제 활동 자료는 UC-ACTIVITY-001로 수집하고 필요한 실행 피드백은 UC-ACTION-001로 연결한다.

대안·예외:

- 1단계 필요한 조건이 부족하면 부족한 부분을 표시한다. 빈 일정을 운동할 수 있는 시간으로 확정하지 않는다.
- 여건이 바뀌어 계획을 조정하려면 UC-PLAN-002로 연결한다.
- 지원 안내 범위 밖이거나 생성에 실패하면 제공 가능하다고 표시하지 않고 기존 기록·계획을 유지한다.

### 비기능 요구사항

- NFR-USABILITY-001: 안내 내용·적용 조건을 확인하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 안내 조회·생성 시간을 구분해 측정한다. 목표는 미정이다.
- NFR-PRIVACY-001: 운동 지침·생활 여건 등 개인 조건의 보관·전송 범위를 확인한다.

## UC-ACTION-001: 실행 결과와 간단한 피드백 남기기

### 개요

실제 식사·운동의 수행 여부와 자동으로 알 수 없는 짧은 보완 정보를 남긴다. 연결 요구: REQ-RECORD-001, REQ-INTERACT-002, REQ-PLAN-004. 실행 기록은 사용자 방향, 해봄·못함·부담 등 문항은 개발 제안이다(Q-09).

### 관련 액터

- 주 액터: 사용자. 알림 경로에서는 Android 알림 시스템이 보조 액터로 참여한다.

### 우선순위

P1(높음·제안). 관찰·추천을 일일 상호작용과 다음 조정으로 연결한다.

### 선행 조건

- 사용자가 기록할 실제 행동·실행 결과 또는 응답할 확인 항목이 있다. 계획 밖 행동도 기록할 수 있으므로 승인 계획은 필수 전제가 아니다.

### 후행 조건

- 성공: 실제 수행 여부·보완 응답이 해당 사건과 연결되어 다음 분석·조정에 사용된다. 계획 항목과 실제 기록은 구분된다.
- 취소·무응답·실패: 기존 성공 기록을 유지한다. 알림 해제·무응답을 완료·미수행·승인으로 대신 해석하지 않는다.

### 이벤트 흐름

트리거: 사용자가 행동 뒤 기록하거나 앱의 실행 확인 요청에 응답한다.

기본 흐름:

1. 시스템이 해당 행동과 이미 수집한 자료를 보여주고 필요한 응답만 제시한다.
2. 사용자가 수행 여부 또는 합의할 간단한 피드백을 남긴다.
3. 시스템이 대상·중복 여부를 확인하여 응답을 실제 기록에 연결·저장한다.
4. 저장 결과를 알리고 이후 기간 분석·필요한 계획 조정의 입력으로 사용한다.

대안·예외:

- 빠른 응답 경로는 UC-INTERACT-002의 상태 확인·저장을 재사용한다. 같은 응답으로 별도 중복 기록을 생성하지 않는다.
- 자동으로 가져온 운동 값은 반복 입력하게 하지 않는다. 결제만으로 먹은 음식·섭취 사실을 채우지 않는다.
- 미수행이라고 직접 응답한 경우와 응답하지 않은 경우를 구분한다. 이유·부담의 필수 여부는 미정이다.
- 저장 실패·오래된 알림·취소는 현재 상태를 확인하고 성공·중복 완료로 표시하지 않는다. 계획 수정이 필요하면 UC-PLAN-002로 연결한다.

### 비기능 요구사항

- NFR-USABILITY-001: 대표 실행 피드백의 필수 입력·조작 수·시간을 측정한다.
- NFR-DATA-001: 성공 저장한 수행·피드백 정보가 정상 재실행 후 유지되는지 확인한다.
- NFR-LOCK-001: 잠금 상태에서 피드백할 때 노출·인증 정책을 확인한다.
- NFR-CAPTURE-001: 사건 뒤 응답 지연과 반복 입력 부담을 측정한다.

<a id="uc-budget-001"></a>

## UC-BUDGET-001: 기간별 실제 식비와 계획 비용 확인하기

### 개요

월·주 등 기간의 실제 결제·예상 비용·미상 정보를 구분하여 예산과 비교한다. 연결 요구: REQ-BUDGET-001, REQ-REVIEW-001, REQ-PLAN-003. 식비 관리 목적은 사용자 방향, 집계·회고 상세는 개발 제안이다. 식비 포함 항목·월/주 경계·취소·환불·초과 처리는 Q-01/Q-03/Q-14 등에서 결정한다.

### 관련 액터

- 주 액터: 사용자. 자료 제공 시스템은 앞선 수집 사례에서 참여하며 이 조회의 필수 호출 대상이 아니다.

### 우선순위

P1(높음·제안). 계획 비용과 실제 식비를 혼동·중복하지 않고 예산을 점검하는 핵심 흐름이다.

### 선행 조건

- 조회할 기간을 정할 수 있다. 기록·예산·계획이 없는 경우도 구분하여 조회하며 모두 존재해야 시작할 수 있는 것은 아니다.

### 후행 조건

- 성공: 기록 범위 안의 실제 식비·예상 비용·예산·미상 범위를 구분하여 확인한다. 장보기 결제와 끼니별 추정 원가를 실제 식비에 중복 합산하지 않는다.
- 부족·실패: 완전한 지출을 파악했다고 표시하지 않는다. 조회 자체가 실제 지출·승인 계획을 수정하지 않는다.

### 이벤트 흐름

트리거: 사용자가 기간별 지출·예산 점검을 요청한다.

기본 흐름:

1. 시스템이 대상 기간·현재 예산·기록된 지출과 확인 상태를 조회한다.
2. 합의할 분류·집계 규칙에 따라 실제 식비를 정리하고 예상 비용은 별도로 다룬다.
3. 실제·예상·미상 범위와 예산 비교를 표시한다.
4. 사용자가 기록 오류를 발견하면 UC-RECORD-001, 계획 조정이 필요하면 UC-PLAN-002로 연결한다.

대안·예외:

- 예산이 없으면 비교 기준이 없음을 표시한다. 기록 없음·연결 단절을 실제 지출 0원으로 표시하지 않는다.
- 중복 후보·혼합 구매·분류 미확정·취소/환불은 확정된 식비와 구분한다. 상세 집계 정책을 이 문서로 확정하지 않는다.
- 조회·집계 실패는 실패로 표시한다. 초과 예상 시 경고·대안·승인 방식은 미정이며 임의로 계획을 바꾸지 않는다.

### 비기능 요구사항

- NFR-PERFORMANCE-001: 기간·자료량별 지출 조회·집계 시간을 측정한다. 목표 수치는 미정이다.
- NFR-USABILITY-001: 실제·예상·미상 및 예산 비교를 구분하는 과제의 조작 수·시간을 측정한다.
- NFR-PRIVACY-001: 금액·가맹점 등 지출 자료의 보관·전송 범위를 확인한다. 잠금화면에 연결할 경우 NFR-LOCK-001도 적용한다.

<a id="uc-review-001"></a>

## UC-REVIEW-001: 실행·지출을 돌아보고 다음 조정 검토하기

### 개요

기록된 실행·지출·부담을 돌아보고 다음 변화의 근거로 사용한다. 연결 요구: REQ-REVIEW-001, REQ-ROUTINE-004, REQ-PLAN-004. 기존 회고 흐름의 개발 제안이며 비교 지표·충족 조건·다음 계획 연결 방식은 초안이다.

### 관련 액터

- 주 액터: 사용자. 외부 AI로 요약·변경 후보를 생성하도록 선택하면 보조 액터로 참여한다. 점검 안내 경로는 Android 알림 시스템이 지원할 수 있다.

### 우선순위

P2(보통·제안). 실행 결과를 모아 다음 기간의 변화를 검토하는 상세 흐름이다.

### 선행 조건

- 점검할 기간과 기록 유무·수집 범위를 조회할 수 있다. 계획이 없던 관찰 기간도 점검할 수 있으며 계획 대비 비교는 해당 계획이 있을 때 수행한다.

### 후행 조건

- 성공: 기간의 기록 범위·실행·지출·확인된 부담과 다음 검토 후보를 확인한다.
- 부족·미선택·실패: 실제 기록·승인 계획을 유지한다. 기록량 증가만으로 생활이 개선됐거나 체중·근육량이 변했다고 판정하지 않는다.

### 이벤트 흐름

트리거: 사용자가 기간 점검을 요청하거나 동의한 점검 안내를 확인한다.

기본 흐름:

1. 시스템이 대상 기간·실제 수집 범위와 관련 계획 유무를 확인한다.
2. 실제 실행·지출·피드백을 정리하고 계획이 있으면 알려진 결과와 비교한다.
3. 근거·미상 정보를 구분하여 다음 검토할 부분을 제시한다.
4. 사용자가 필요한 경우 분석 정정·변경 후보·계획 조정 사례로 이어간다.

대안·예외:

- 자료가 부족하면 해석할 수 있는 범위와 부족 정보를 표시한다. 집계 기준·추세 판단 조건은 미정이다.
- 실제 기록 오류는 UC-RECORD-001, 해석 오류는 UC-ANALYSIS-002로 구분한다.
- 요약 실패·사용자 미선택은 새 계획 승인으로 처리하지 않는다. 자동으로 승인 계획을 대체하지 않는다.

### 비기능 요구사항

- NFR-USABILITY-001: 실행·지출·미상 정보를 확인하고 다음 검토로 연결하는 과제의 조작 수·시간을 측정한다.
- NFR-PERFORMANCE-001: 기간·자료량별 회고 조회·생성 시간을 구분해 측정한다.
- NFR-PRIVACY-001: 회고 자료의 외부 전달·보관 범위를 확인한다.

<a id="uc-settings-001"></a>

## UC-SETTINGS-001: 알림·정보 노출과 데이터 처리 범위 확인하기

### 개요

지원되는 알림·잠금화면 정보 노출을 조정하고 외부 전송·보관·삭제 정책을 확인한다. 연결 요구: REQ-INTERACT-001, NFR-LOCK-001, NFR-PRIVACY-001. 노출 제어는 요구이며 상세 기본값·정책은 개발 제안이다(Q-05/Q-07/Q-13). 실제 데이터 삭제 실행 기능은 확정하지 않는다.

### 관련 액터

- 주 액터: 사용자. 보조 액터: Android 권한·알림 시스템.

### 우선순위

P1(높음·제안). 지속 수집·알림에서 사용자가 접근과 정보 노출을 이해·제어하는 경계다.

### 선행 조건

- 설정·정책 확인에 접근할 수 있다. 모든 수집·알림 권한이 부여돼 있을 필요는 없다.

### 후행 조건

- 성공: 데이터 처리 안내와 현재 노출·알림 상태를 확인하고 지원되는 변경을 실제 적용 상태와 구분하여 알 수 있다.
- 취소·실패·OS 제한: 기존 적용 상태를 유지하거나 실제 OS 상태를 표시한다. 적용하지 못한 설정을 적용 완료로 표시하지 않는다.

### 이벤트 흐름

트리거: 사용자가 설정·데이터 처리 정책 확인 또는 변경을 요청한다.

기본 흐름:

1. 시스템이 현재 앱·OS의 알림·노출 상태와 데이터 처리 안내를 보여준다.
2. 사용자가 지원 범위에서 알림·잠금화면 노출을 조정하거나 정책을 확인한다.
3. 필요한 OS 설정을 거쳐 실제 상태를 확인하고 앱에서 저장할 선택값을 저장한다.
4. 현재 적용 상태와 제한을 보여준다.

대안·예외:

- 정책 조회만 하면 3단계 변경 저장 없이 종료한다. 미정인 전송·보관·삭제 기준을 확정 정책이라고 표시하지 않는다.
- OS 알림 차단·권한 회수·잠금 상태 제한이 있으면 실제 제약을 표시한다. 앱 설정만으로 강제 표시·인증 생략을 보장하지 않는다.
- 저장 실패는 성공으로 표시하지 않는다. 데이터 출처별 접근 변경은 UC-LINK-001로 연결하며 알림 차단과 수집 권한을 구분한다.
- 구체적 빈도·미루기·기본 노출값, 데이터 삭제 실행·오프라인 보장·외부 AI 동의 흐름은 별도 미정 사항이다.

### 비기능 요구사항

- NFR-PRIVACY-001: 안내한 전송·보관·삭제 방식과 실제 구현 정책의 일치 여부를 검증하도록 연결한다. 정책 자체는 Q-07에서 정한다.
- NFR-LOCK-001: 잠금·해제·설정 조합별 실제 노출·인증·진입 경로를 확인한다.
- NFR-USABILITY-001: 현재 적용 상태와 변경할 항목을 식별하는 과제의 조작 수·시간을 측정한다.

<a id="uc-routine-001"></a>

## UC-ROUTINE-001: 기존 루틴 파악과 첫 변경 제안 — 전체 여정

### 개요

관리 방향 선택·기존 생활 관찰·분석을 거쳐 적합한 변경을 선택하고 첫 기간 계획 검토로 이어지는 전체 여정이다. 하위 사례를 묶는 기존 ID이며 별도 신규 기능으로 세지 않는다. 연결 요구: REQ-GOAL-001, REQ-GOAL-002, REQ-ROUTINE-001, REQ-ROUTINE-002, REQ-ROUTINE-003, REQ-ROUTINE-004, REQ-CHANGE-001, REQ-PLAN-003. 큰 방향은 사용자 의도 확인, 확인 순서·분석 정정·자료 충족 조건은 초안이다(Q-02/Q-08/Q-09/Q-10).

### 관련 액터

- 주 액터: 사용자.
- 보조 액터: 허용한 결제·건강 자료 제공 시스템, Android 권한·알림 시스템. 외부 AI를 선택하면 분석·제안의 보조 액터로 참여한다.

### 우선순위

P1(높음·제안). 기존 생활을 먼저 이해한 뒤 바꾸는 핵심 제품 여정이다.

### 선행 조건

- 신규 사용 또는 기존 루틴을 다시 파악하려는 상태다. 새 계획 승인·신체 측정값은 필요하지 않다.
- 자동 수집의 출처·권한은 여정 안에서 선택한다. 권한이 없거나 자료가 부족한 경우를 구분한다.

### 후행 조건

- 성공: 관찰 근거와 실행 여건을 확인하고 시도할 변경을 선택하여 계획 검토로 연결한다. 계획 승인·저장 성공 여부는 UC-PLAN-001에서 별도로 판단한다.
- 부족·취소·실패: 기존 성공 기록·승인 계획을 보존한다. 적합한 변화가 없으면 찾았다고 표시하지 않고 관찰 전에 새 식사·운동 수행을 강요하지 않는다.

### 이벤트 흐름

트리거: 사용자가 앱 사용을 시작하거나 기존 루틴의 재관찰을 요청한다.

기본 흐름:

1. UC-GOAL-001과 필요한 UC-PROFILE-001에서 관리 방향·알려진 실행 여건을 확인한다. 한 번에 모든 조건을 입력받는 방식은 아니다.
2. UC-LINK-001로 허용 범위를 정하고 UC-CAPTURE-001 및 UC-RECORD-001로 평소 생활을 기록한다.
3. UC-ANALYSIS-001에서 대상 기간·실제 자료·근거·미상 정보를 요약한다.
4. 사용자가 필요한 해석·가용 시간을 확인·정정하고 UC-CHANGE-001에서 변경 후보를 검토·선택한다.
5. UC-PLAN-001의 검토·승인으로 연결한다. 이후에도 수집·짧은 응답·기간 분석·일일 조정을 계속한다.

대안·예외:

- 출처 미지원·권한 거부·미응답은 수집 실패·미상과 구분하고 기록 보완 흐름으로 연결한다. 실제 지원·보완 정책은 미정이다.
- 3단계 자료 부족은 분석 가능한 범위·부족 정보를 표시한다. 3·7·15일 경과만으로 충분한 관찰·확정 패턴이라고 판단하지 않는다.
- 4단계 알려진 조건에 맞는 후보가 없으면 관찰·추가 확인이 필요함을 구분한다. 상세 정책은 미정이다.
- 분석·제안·저장 실패나 사용자의 미선택은 새 계획 승인으로 처리하지 않는다. 하위 사례의 보존·실패 규칙을 따른다.

### 비기능 요구사항

- NFR-USABILITY-001: 초기 설정·관찰 보완·분석 확인·변경 선택까지의 과제별 입력·조작 수·시간을 측정한다.
- NFR-CAPTURE-001: 초기 관찰 이후에도 지속되는 수집·알림의 지연·배터리 부담을 확인한다.
- NFR-PRIVACY-001, NFR-LOCK-001: 전체 여정의 외부 전송·보관 안내와 잠금 상태 노출을 확인한다.
- NFR-DATA-001, NFR-PERFORMANCE-001: 성공 저장한 자료의 정상 재실행 후 보존과 단계별 응답 시간을 확인한다. 기준 수치는 미정이다.

## UC-CAPTURE-001: 사건 기반 자동 수집과 빠른 확인 — 전체 여정

### 개요

출처 연결·지원 자료 수집·필요한 빠른 확인을 묶어 앱 사용 기간 내내 실제 기록을 축적하는 전체 여정이다. 기존 ID이며 하위 사례와 중복 집계하지 않는다. 연결 요구: REQ-INGEST-001, REQ-INGEST-002, REQ-INGEST-003, REQ-INGEST-004, REQ-INTERACT-001, REQ-INTERACT-002, REQ-ROUTINE-001, REQ-RECORD-001. 자동화·짧은 상호작용은 사용자 방향, 지원 경로·정확성·권한·확인 상세는 초안이다(Q-05/Q-09/Q-11/Q-12/Q-13/Q-14).

### 관련 액터

- 수혜·응답 액터: 사용자. 자료 도착 시 결제·건강 자료 제공 시스템이 시작 액터가 된다.
- 보조 액터: Android 권한·알림 시스템. 자료 저장·중복 확인은 앱 내부 책임이다.

### 우선순위

P1(높음·제안). 전체 관찰·실행 단계에서 직접 입력을 최소화하는 반복 여정이다.

### 선행 조건

- 사용자가 연결을 설정할 수 있다. 개별 자료 수집 시에는 해당 범위의 권한·지원 조건이 성립해야 한다.
- 기존 계획·최초 관찰 완료는 필요하지 않다. 승인·분석 여부와 별개로 수집을 계속한다.

### 후행 조건

- 성공: 지원 자료·출처·처리 상태와 필요한 사용자 응답이 기록되어 분석·조정에 사용된다. 별도 확인이 필요 없는 자료는 응답을 수집 완료의 필수 조건으로 삼지 않는 방향이다.
- 부분·무응답·실패: 자동으로 가져온 사실과 아직 미확인인 내용을 구분한다. 기존 성공 기록을 보존하며 지출·활동 0 또는 계획 변경 승인으로 간주하지 않는다.

### 이벤트 흐름

트리거: 최초 연결 요청, 허용한 지원 사건 도착 또는 수집 작업 실행. 같은 여정을 초기 관찰·이후 실행 중 반복한다.

기본 흐름:

1. 최초 연결·권한 설정이 필요하면 UC-LINK-001과 UC-SETTINGS-001을 거친다.
2. 도착한 자료에 따라 UC-EXPENSE-001 또는 UC-ACTIVITY-001에서 출처·시각·중복·정정·취소를 구분하여 저장한다.
3. 필요한 확인이 남으면 UC-INTERACT-001로 알리고 UC-INTERACT-002에서 짧은 응답을 받는다.
4. 해당 실제 기록·확인 상태를 보존하고 UC-ANALYSIS-001 및 필요한 UC-PLAN-002의 입력으로 연결한다.

대안·예외:

- 1~2단계 권한 거부·회수·미지원 형식·동기화 지연은 해당 하위 사례의 상태로 표시한다. 재연결·과거 보완·재시도 범위는 미정이다.
- 2단계 중복·정정·취소는 같은 실제 사건의 상태와 구분하며 수집 건수만큼 지출·활동을 늘리지 않는다.
- 3단계 알림 차단·잠금 제약·미응답은 미처리 확인 항목으로 유지한다. 식사·운동 직후 항상 도착하거나 잠금 해제 없이 처리한다고 보장하지 않는다.
- 재부팅·오프라인·강제 종료 조건의 복구·수집 재개 범위는 기기 시험·저장 정책에서 정한다. 정상 재실행 보존 요구를 모든 상황의 무손실 보장으로 확대하지 않는다.

### 비기능 요구사항

- NFR-DATA-001: 성공 저장한 자료·응답·처리 상태가 정상 재실행 후 조회되는지 확인한다.
- NFR-USABILITY-001, NFR-CAPTURE-001: 자동 수집 후 남은 수동 조작 수·시간과 지연·배터리 부담을 함께 측정한다.
- NFR-PRIVACY-001, NFR-LOCK-001: 수집·전송·보관 안내와 잠금 상태의 정보 노출·응답 경로를 확인한다.
- NFR-PERFORMANCE-001: 수집 뒤 조회·응답 저장 등 단계별 응답 시간을 측정한다. 기준 기기·자료량·목표 수치는 미정이다.

## 문서 검토와 후속 작업

각 사례의 일곱 항목, 연결 요구·Q 번호, 우선순위와 목록 ID의 일치 여부를 확인한다. 이 문서의 이벤트 흐름은 후속 활동도·시퀀스·화면 설계·검증 시나리오의 입력으로 사용한다. UML의 `include`·`extend`나 코드 클래스 수를 여기서 자동으로 결정하지 않는다.

우선 수집·빠른 확인의 필수 확인 항목(Q-09/Q-14), 분석 창·충족 조건(Q-08), 승인 단위·위임(Q-01/Q-06)을 구체화한다. 비기능 요구의 허용 수치와 실제 연동·잠금 동작은 대표 과제와 기기 시험 후 합의한다. 아직 앱 코드·빌드·자동 테스트·실기 검증은 수행하지 않았다.
